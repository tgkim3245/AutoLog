4. Zipy 네트워크 준비

  1. 설정 → Ethernet 연결에서 배포 폴더의 캡처 도구가 표시되는지 확인합니다. 처음 사용할 때는 동봉된 tools/Wireshark/tshark.exe를 자동으로 사용합니다. 배포 폴더를 옮겨도 동봉 도구를 다시 찾습니다. 다른 설치본이 필요하면 직접 선택으로 지정하세요. 그 설치 폴더에도 dumpcap·capinfos가 있어야 합니다.
  2. 장비에 연결된 네트워크를 이름으로 클릭해 선택합니다. 선택한 이름이 입력란에 표시되는지 확인하세요. 목록 오른쪽 그래프는 해당 어댑터 전체의 수신량이므로 참고용으로 사용하세요.
  3. 저장 형식 pcap(기본) 또는 pcapng를 선택하고 연결 확인을 누릅니다. 실제 취득은 메인의 기록 시작을 눌러 시작합니다.

TShark 경로·네트워크·형식을 기억합니다. 필요한 도구는 별도 설치 안내를 따릅니다. 캡처 버퍼는 고정이며 저장할 수 있는 파일의 최대 크기를 뜻하지 않습니다.

5. 저장 설정과 기록 시작·정지

  1. 설정 → 저장 설정에서 저장 위치를 선택하고 파일 prefix와 다음 저장 인덱스를 입력한 뒤 적용합니다. 파일·네트워크 경로 선택은 자동으로 기억하며 prefix·다음 번호는 적용 후 사용합니다.
  2. 메인의 CAN·Diag·Zipy 중 이번에 사용할 대상을 선택합니다. 준비되지 않은 대상은 해제하거나 먼저 연결을 준비하세요.
  3. 초록색 기록 시작을 누릅니다. 기록 중에는 같은 버튼이 빨간색 기록 중 · 정지로 바뀌며, 누르면 기록을 마칩니다.
  4. 정지와 파일 검사·보관이 끝날 때까지 기다린 뒤 최종 파일명과 저장 위치를 확인합니다. 일부 실패·미완료 표시는 전체 성공을 뜻하지 않습니다.

CAN·Diag는 선택한 블록의 기록을 정지한 뒤 이번 BLF의 마지막 버퍼와 헤더를 완성하고 검사·보관합니다. CANoe가 다음 trigger에서 파일을 완성하는 경우, 별도 내부 파일로 짧게 전환한 후 정지하여 이번 BLF를 완성합니다. 측정·다른 블록은 유지하며 내부 전환 파일을 사용자 로그로 보관하거나 번호를 추가 소비하지 않습니다. 보관 완료 뒤 같은 버튼으로 다음 기록을 시작할 수 있습니다. 파일 핸들이 남아 있어도 완전한 안정된 복사본을 만들 수 있으면 보관하며, 큰 파일은 검사·복사 시간이 추가될 수 있습니다.

.vil_work는 기록 중·마무리 중인 파일을 완료 파일과 구분하는 내부 작업 폴더입니다. 완성된 사용자 BLF·PCAP는 지정한 저장 폴더의 최종 이름으로 보관합니다. 실제 BLF가 완성되지 않았는데 임시 폴더를 없애거나 헤더만 고쳐 정상 파일로 표시하지 않습니다.

정지·보관 확인 필요는 파일이 없다는 뜻이 아닙니다. 기록 정지나 파일 완결·보관을 확인하지 못해 생성된 파일을 보존한 상태입니다. 아직 변하거나 잘린 파일을 정상 완료로 표시하지 않습니다. 복구 화면에서 실제 파일과 실패 원인을 확인하고, 계속 실패하면 버그리포트를 보내 주세요.

초기 파일명은 cfg에서 읽으며 고정하지 않습니다. CANoe의 trigger 자동 번호가 켜져 있으면 복구 후 _T002 또는 _T002_T001처럼 번호가 붙을 수 있습니다. 우리 복구 과정에서 같은 원래 이름·폴더에 붙은 trigger 번호는 처리합니다. 임의의 다른 필드 코드 변환까지 지원한다고 보장하지 않습니다. 기록 중 임의로 파일명이나 옵션을 바꾸지는 마세요.

CANoe가 마지막 내부 전환 파일을 열어 두면 .vil_work가 잠시 남을 수 있습니다. 정상 보관한 파일은 유지하고 내부 파일은 핸들이 해제되면 정리합니다. X 또는 예기치 않은 종료로 중단된 구간의 임시 파일은 삭제하며, 잠긴 파일은 정리를 재시도합니다. 중단 이력 때문에 다음 기록을 막지 않습니다.

CANoe가 cfg의 기존 출력 이름을 다시 받지 않으면 기존 출력 경로 복구 보류 · 다음 기록은 계속할 수 있습니다가 표시될 수 있습니다. 이미 정지한 {{APP_NAME}} 소유 블록임을 확인한 경우 다음 기록을 허용하며, 최종 BLF 검사·보관은 그대로 수행합니다. 원본 cfg는 자동 저장하지 않습니다. 복구가 보류된 임시 출력 경로를 CANoe 구성에 저장하지 마세요. 외부에서 블록·파일명·옵션을 바꾸거나 수동 기록을 켜면 이 예외를 적용하지 않습니다.

6. 완료 파일 관리와 임시 폴더

  • 메인 상단 로깅 대상 줄의 로그 폴더는 사용자가 지정한 캡처 저장 폴더를 엽니다. 파일 영역의 작업 이력은 직전 로그 지우기 왼쪽 같은 행에 있습니다.
  • 직전 파일 이름 입력란에서 Enter를 누르거나 이름 변경 버튼을 누르면 입력한 이름을 그대로 사용하며 번호를 붙이지 않습니다. 확장자는 유지하고 Diag에는 _Diag가 붙습니다. 예: 주행 기록.blf, 주행 기록_Diag.blf. 기록·파일 처리 중에는 이름을 바꿀 수 없습니다.
  • 직전 로그 지우기에서 대상 경로를 확인한 뒤 삭제합니다. 영구 삭제 확인 후에는 휴지통을 거치지 않습니다. 작업 이력은 기존 이름 변경·삭제 등의 결과와 원본/변경 경로를 읽기 전용으로 보여줍니다. 위쪽 로그 폴더에서 사용자 저장 위치를 열 수 있습니다.
  • .vil_work는 기록·검사를 위한 임시 작업 폴더입니다. X로 중단하거나 예기치 않게 종료한 구간은 자동 정리합니다. 저장 완료된 최종 파일은 삭제하지 않습니다. 기록·파일 처리가 진행 중이면 직접 지우지 마세요.

사용 중·외부 변경·닫힘 미확인 파일은 처리가 보류될 수 있습니다. 작업 이력의 결과와 실제 경로를 확인하세요. 설정·번호·이력은 PC/Windows 사용자별로 기억합니다. 이전 AutoLog 프로그램을 완전히 종료하고 새 프로그램을 처음 실행하면 기존 프로필을 새 {{APP_NAME}} 프로필로 복사합니다. 사용자 지정 경로·prefix·번호·규칙은 유지하고, 기존 기본 prefix만 One_Click_Log로 바꿉니다. 원래 DB와 캡처 파일은 이동하거나 삭제하지 않습니다.

7. 최근 활동·통신 감시

  • 최근 활동은 500건까지 표시합니다. 전체/경고·오류/오류 필터와 항목 복사로 발생 시각·원문·상세를 확인할 수 있습니다.
  • 메인의 통신 감시·기록 품질·패킷 보기와 설정의 환경 확인 기능은 제거했습니다. 원본 패킷 분석은 저장된 파일을 Wireshark에서 여세요. 연결 설정은 톱니바퀴에서 합니다.
  • 설정 → zipy 유효성검사에는 기본 Zipy 규칙이 들어 있습니다. Source MAC이 02:00:00으로 시작하는 패킷의 2초 평균 수신량을 확인합니다. 다른 Source와 프로토콜도 모두 저장하며 이 규칙은 캡처 필터가 아닙니다. 기본값은 시작 유예 5초, 미수신 제한 3초, 최소 100pps입니다. 최소량 미달이 3초 지속되어도 정지합니다. 해당 장비의 실제 정상 수신량에 맞춰 수정할 수 있고 0pps는 수신량 하한만 해제합니다. 규칙 삭제는 그 규칙의 수신 감시를 해제합니다. CAN·Diag의 실제 수신 감시는 현재 미지원입니다.

선택한 네트워크 단절, 감시 기준 위반, 기록 도구 오류가 확인되면 선택한 모든 대상을 함께 정지하고 정상적으로 닫힌 파일을 검사·보관합니다. 감시에서 한 번 확인한 기준 위반은 화면 갱신 전에 수신이 복구돼도 정지 사유로 유지합니다. 감시 해석/응답 확인 불가가 5초 지속돼도 정지합니다. 실패 원인은 최근 활동과 버그리포트에 남기며 전체 성공으로 표시하지 않습니다. 케이블·장비·설정을 확인한 뒤 초록색 새 기록 시작으로 새 구간을 취득하세요. 어댑터 링크가 살아 있는 상위 구간 단선은 필요한 Source의 수신 감시로 확인합니다. 인터넷 연결 여부는 판단 기준이 아닙니다. 상단 한 | EN | 中 버튼으로 언어를 바꿀 수 있습니다.

기본 규칙 이름은 “Zipy 활성화 실패”입니다. 위반을 확인하면 기록 정리와 별도로 팝업을 띄웁니다. 기본 안내는 “Zipy 데이터 활성화에 실패하였습니다. Render 터미널에 아래의 커맨드를 입력하세요. |6 → e1”입니다. 팝업 안내 문구에서 규칙별 문구와 줄바꿈을 수정하거나 새 규칙에 안내를 추가할 수 있습니다. 비워 두면 일반 안내를 표시합니다. 저장한 문구는 언어 선택과 관계없이 그대로 표시되며, 기록 중에는 기준·문구 편집이 잠깁니다. 같은 구간의 같은 실패로 팝업을 반복 표시하지 않고, 팝업이 열려 있어도 파일 정리와 메인 X 종료는 막지 않습니다.

CAN·Diag도 기록 중 CANoe 측정 중지, 선택한 기록 블록 중지, CANoe 응답·기록 상태 확인 불가를 확인하면 “기록 중단 알림” 팝업을 띄우고 선택한 기록을 모두 정지합니다. 이상이 생긴 대상과 확인한 원인을 표시하며, 여러 대상이 동시에 실패하면 알림 하나로 묶습니다. 정상적으로 닫힌 파일은 보관을 시도하고 결과는 최근 활동에 남깁니다. 알림 확인을 기다리느라 파일 정리나 X 종료가 지연되지는 않습니다.

CAN 장비 USB·전원 분리 등으로 CANoe 측정/기록이 중단된 경우의 알림이며, 물리 배선을 직접 판별하는 기능은 아닙니다. 차량 쪽 CAN 통신선만 빠져도 CANoe 측정과 기록이 계속되면 현재 자동 감지하지 못합니다. CAN·Diag의 실제 수신 감시는 미지원입니다. 팝업이 없다는 이유로 수신이 정상이라고 판단하지 말고 CANoe Trace를 확인하세요. 알림 후에는 USB·전원·케이블과 CANoe의 라이선스/컴파일 오류를 확인하고 측정(F9)·Trace 수신을 복구한 뒤 새 기록을 시작하세요.

9. 버그리포트 보내기

  1. 문제 발생 시 상단 버그리포트 버튼을 누릅니다.
  2. 바탕화면의 One_Click_Log_BugReport_To_Taegon.Kim_날짜_시각_고유번호.zip을 확인합니다.
  3. 발생 시각, 선택한 대상, 누른 버튼 순서, 필요하면 CANoe Write 창 오류를 함께 적어 Taegon.Kim에게 해당 파일을 이메일로 보냅니다. 앱에서 자동 발송하지 않습니다.

개발자로그는 항상 EXE 옆 developer_logs에 순환 저장하며, 기본 5MB 파일과 최대 4개 백업을 유지합니다. ZIP에는 최근 로그와 원본 크기·해시 목록이 들어갑니다. 압축 때문에 ZIP과 원본 파일 크기가 다른 것은 정상입니다. 실제 캡처 파일과 cfg 전체를 ZIP에 자동 첨부하지 않습니다.
