0처음 쓰는 PC: 초기설정부터

CANoe 버전은 사용할 RBS 구성(.cfg)에 맞춰 선택합니다. 해당 버전의 프로그램·라이선스·Vector 드라이버를 먼저 준비하세요. BAT가 설치된 64비트 CANoe를 검색해 버전과 경로를 보여주며, 사용자가 선택한 설치본을 기본 COM 대상으로 등록합니다.

  1. 배포 ZIP 전체를 로컬 폴더에 압축 해제합니다. One Click Log와 모든 CANoe 작업을 저장하고 종료합니다.
  2. EXE 옆 Initial_Setup.bat를 더블클릭합니다. 현재 COM 대상과 검색된 CANoe 버전·설치 경로를 확인한 뒤 사용할 설치본의 목록 번호를 입력합니다. 하나만 있어도 직접 선택하며 빈 입력 또는 Q는 등록 취소입니다. 서명 없는 파일은 경로·SHA256을 확인하고 신뢰하는 공식 설치본일 때만 REGISTER를 추가 입력합니다. 확인할 수 없으면 취소하세요.
  3. 공식 도구의 관리자 요청을 승인합니다. BAT가 선택한 CANoe를 앱의 기본 CANoe(COM 자동 연결 대상)로 등록하고 경로·버전 일치를 확인합니다. 이어 Npcap이 있으면 건너뛰고, 없으면 동봉 설치 파일을 자동으로 관리자 실행합니다.
  4. BAT가 자동으로 연 Npcap 공식 설치창에서 라이선스·옵션을 확인하고 설치를 마칩니다. 재부팅 요청이 있으면 재부팅한 뒤 BAT를 다시 실행해 확인합니다. 사용할 기능의 결과(CAN·Diag: CANoe: 0, Zipy: Npcap: 0)를 확인한 뒤 앱을 실행해 아래 연결·기록 순서를 진행합니다.

BAT가 설치 파일을 찾아 자동 실행하며, 관리자 승인과 공식 설치창의 동의·확인은 사용자가 합니다. 설치가 진행되지 않거나 파일 누락 오류가 나올 때는 Npcap 초기설정·예외 조치를 확인하고 단계 결과와 BAT 로그를 보관하세요.

초기설정을 마쳤으면 {{APP_NAME}}.exe를 실행하세요.

처음 쓰는 PC라면 먼저 확인하세요

CAN·Diag: RBS 구성(.cfg)에 맞는 CANoe·드라이버·라이선스와 프로젝트 전체를 먼저 준비합니다. Zipy: Npcap은 초기설정 BAT가 설치 여부를 확인해, 없으면 동봉 설치 파일을 자동으로 관리자 실행합니다. BAT에서 사용할 CANoe 버전도 선택하세요. TShark는 동봉돼 있습니다.

초기설정과 Npcap 설치는 위의 BAT 절차를 따르세요. EXE 옆 _internal·tools 폴더는 함께 유지합니다. .cbf 액세스 거부가 나오면 Vector 앱 허용 방법을 확인하세요.

초기설정 BAT의 Npcap 자동 설치 안내

기본 절차는 ZIP 전체를 푼 뒤 EXE 옆 Initial_Setup.bat를 실행하는 것입니다. BAT가 Npcap 설치 여부를 확인하고, 이미 있으면 건너뛰며 없으면 동봉 설치 파일을 자동 실행합니다.

  1. One Click Log와 모든 CANoe 작업을 저장·종료한 뒤 EXE 옆 Initial_Setup.bat를 더블클릭합니다. 검색된 CANoe 목록에서 사용할 설치본의 번호를 입력하고 공식 도구의 관리자 권한 요청을 승인합니다.
  2. BAT가 연 Npcap 공식 설치창에서 라이선스·옵션을 확인하고 동의·설치 완료를 진행합니다. Windows 관리자 요청도 승인합니다. 재부팅 요청 시 재부팅한 뒤 BAT를 다시 실행해 확인하세요.
  3. One Click Log를 다시 열고 설정 → Ethernet 연결 → 네트워크 선택 → 연결 확인으로 준비합니다.

예외 — BAT가 설치 파일 누락을 알리면 ZIP 전체가 압축 해제됐는지 먼저 확인하세요. Npcap 설치 파일은 확인된 회사 내부 PC 1대용 배포에 동봉하며, 조건은 LICENSE.txt와 Npcap 공식 안내를 따릅니다. 설치 파일을 포함하지 않는 일반 배포를 받은 경우에만 PC 관리자 또는 공식 사이트를 통해 준비하세요.

CANoe 창이 열리지 않나요? (버전 설치·제거 후)

CANoe가 설치돼 있어도 Windows의 자동 연결(COM) 등록이 없어지거나 제거한 버전을 가리키면 앱에서 열 수 없습니다. cfg·채널·라이선스 확인 전에 실패하는 문제입니다.

  1. 모든 CANoe 작업을 저장하고 창을 닫습니다.
  2. 초기설정 BAT에서 RBS 구성에 맞는 CANoe 설치본을 선택하세요. 수동 복구가 필요하면 그 설치 폴더의 Exec64\RegisterComponents.exe를 관리자 권한으로 실행한 뒤 연결을 다시 확인합니다.
  3. 완료 후 One Click Log 설정의 해당 카드에서 연결 확인을 다시 누릅니다. 도구가 없거나 복구가 실패하면 해당 CANoe 설치 복구를 사용하거나 PC 관리자에게 요청하세요.
C:\Program Files\Vector CANoe 19\Exec64\RegisterComponents.exe

위 경로는 CANoe 19 설치 예시이며 필수 버전을 뜻하지 않습니다. RBS 구성에 맞는 설치본을 선택하세요. BAT는 선택한 설치본의 공식 등록 도구를 실행하고 실제 COM 대상이 그 설치본과 일치하는지 확인합니다.

EXE 옆 Initial_Setup.bat는 설치된 64비트 CANoe의 버전·경로와 현재 COM 대상을 표시합니다. RBS 구성에 맞는 목록 번호를 직접 입력하세요. 하나만 발견돼도 자동 선택하지 않습니다. 선택한 실행 파일·공식 등록 도구의 Vector 서명과 등록 후 경로/버전을 확인합니다. Npcap 설치/건너뛰기는 이어 진행합니다. --check는 검색·검사만 하며, RBS 열기 실패 시 하단 재설정 절차를 따릅니다. 서명 없는 설치본은 사용자의 공식 설치본 확인과 REGISTER 추가 입력, 해시 재확인을 거칩니다. 잘못된 서명은 차단합니다.

CAN·Diag는 선택한 블록의 기록을 정지한 뒤 이번 BLF의 마지막 버퍼와 헤더를 완성하고 검사·보관합니다. CANoe가 다음 trigger에서 파일을 완성하는 경우, 별도 내부 파일로 짧게 전환한 후 정지하여 이번 BLF를 완성합니다. 측정·다른 블록은 유지하며 내부 전환 파일을 사용자 로그로 보관하거나 번호를 추가 소비하지 않습니다. 보관 완료 뒤 같은 버튼으로 다음 기록을 시작할 수 있습니다. 파일 핸들이 남아 있어도 완전한 안정된 복사본을 만들 수 있으면 보관하며, 큰 파일은 검사·복사 시간이 추가될 수 있습니다.

.vil_work는 기록 중·마무리 중인 파일을 완료 파일과 구분하는 내부 작업 폴더입니다. 완성된 사용자 BLF·PCAP는 지정한 저장 폴더의 최종 이름으로 보관합니다. 실제 BLF가 완성되지 않았는데 임시 폴더를 없애거나 헤더만 고쳐 정상 파일로 표시하지 않습니다.

정지·보관 확인 필요는 파일이 없다는 뜻이 아닙니다. 기록 정지나 파일 완결·보관을 확인하지 못해 생성된 파일을 보존한 상태입니다. 아직 변하거나 잘린 파일을 정상 완료로 표시하지 않습니다. 복구 화면에서 실제 파일과 실패 원인을 확인하고, 계속 실패하면 버그리포트를 보내 주세요.

초기 파일명은 cfg에서 읽으며 고정하지 않습니다. CANoe의 trigger 자동 번호가 켜져 있으면 복구 후 _T002 또는 _T002_T001처럼 번호가 붙을 수 있습니다. 우리 복구 과정에서 같은 원래 이름·폴더에 붙은 trigger 번호는 처리합니다. 임의의 다른 필드 코드 변환까지 지원한다고 보장하지 않습니다. 기록 중 임의로 파일명이나 옵션을 바꾸지는 마세요.

CANoe가 마지막 내부 전환 파일을 열어 두면 .vil_work가 잠시 남을 수 있습니다. 정상 보관한 파일은 유지하고 내부 파일은 핸들이 해제되면 정리합니다. X 또는 예기치 않은 종료로 중단된 구간의 임시 파일은 삭제하며, 잠긴 파일은 정리를 재시도합니다. 중단 이력 때문에 다음 기록을 막지 않습니다.

CANoe가 cfg의 기존 출력 이름을 다시 받지 않으면 기존 출력 경로 복구 보류 · 다음 기록은 계속할 수 있습니다가 표시될 수 있습니다. 이미 정지한 {{APP_NAME}} 소유 블록임을 확인한 경우 다음 기록을 허용하며, 최종 BLF 검사·보관은 그대로 수행합니다. 원본 cfg는 자동 저장하지 않습니다. 복구가 보류된 임시 출력 경로를 CANoe 구성에 저장하지 마세요. 외부에서 블록·파일명·옵션을 바꾸거나 수동 기록을 켜면 이 예외를 적용하지 않습니다.

6. 완료 파일 관리와 임시 폴더

  • 메인 상단 로깅 대상 줄의 로그 폴더는 사용자가 지정한 캡처 저장 폴더를 엽니다. 파일 영역의 직전 기록 파일 제목, 작업 이력, 직전 로그 지우기는 같은 행에 있으며 작업 이력이 직전 로그 지우기 왼쪽에 있습니다.
  • 직전 파일 이름 입력란에서 Enter를 누르거나 이름 변경 버튼을 누르면 입력한 이름을 그대로 사용하며 번호를 붙이지 않습니다. 확장자는 유지하고 Diag에는 _Diag가 붙습니다. 예: 주행 기록.blf, 주행 기록_Diag.blf. 기록·파일 처리 중에는 이름을 바꿀 수 없습니다.

  • .vil_work는 기록·검사를 위한 임시 작업 폴더입니다. X로 중단하거나 예기치 않게 종료한 구간은 자동 정리합니다. 저장 완료된 최종 파일은 삭제하지 않습니다. 기록·파일 처리가 진행 중이면 직접 지우지 마세요.

사용 중·외부 변경·닫힘 미확인 파일은 처리가 보류될 수 있습니다. 작업 이력의 결과와 실제 경로를 확인하세요. 설정·번호·이력은 PC/Windows 사용자별로 기억합니다. 이전 AutoLog 프로그램을 완전히 종료하고 새 프로그램을 처음 실행하면 기존 프로필을 새 {{APP_NAME}} 프로필로 복사합니다. 사용자 지정 경로·prefix·번호·규칙은 유지하고, 기존 기본 prefix만 One_Click_Log로 바꿉니다. 원래 DB와 캡처 파일은 이동하거나 삭제하지 않습니다.

9. 버그리포트 보내기

  1. 문제 발생 시 상단 버그리포트 버튼을 누릅니다.
  2. 바탕화면의 One_Click_Log_BugReport_To_Taegon.Kim_날짜_시각_고유번호.zip을 확인합니다.
  3. 발생 시각, 선택한 대상, 누른 버튼 순서, 필요하면 CANoe Write 창 오류를 함께 적어 Taegon.Kim에게 해당 파일을 이메일로 보냅니다. 앱에서 자동 발송하지 않습니다.

개발자로그는 항상 EXE 옆 developer_logs에 순환 저장합니다. 기본 회전 기준은 파일당 5 MiB이며 현재 파일과 백업 최대 4개로 약 25 MiB를 유지합니다. 날짜가 아니라 용량 기준이므로 보관 시간을 보장하지 않습니다. 같은 폴더에서 재실행하면 이전 로그에 이어 쓰며, 한도에 도달하면 오래된 내용부터 교체합니다.

버그리포트 버튼을 누를 때 현재 로그와 존재하는 백업, 원본 크기·SHA256 목록을 바탕화면 ZIP으로 복사합니다. ZIP은 그 시점의 스냅샷이며 이후 사건은 추가되지 않습니다. 내보낸 ZIP은 앱이 자동 삭제하거나 수량·기간을 제한하지 않으므로 따로 보관·정리하세요. 압축 때문에 ZIP과 원본 크기가 다른 것은 정상입니다.

오류 직후 ZIP을 저장하고 TC 번호·시험 회차·발생 시각과 시간대·선택 대상·저장 번호·누른 순서·기대 결과와 실제 결과를 함께 보내 주세요. 필요하면 CANoe Write 오류와 화면도 첨부하세요. 실제 BLF·PCAP·PCAPNG, cfg 전체, 설정·이력 DB와 화면 사진은 ZIP에 자동 포함하지 않습니다. 수신 누락·진단 왕복 분석은 해당 원본과 비교 기준을 별도로 준비하세요.

정상 종료는 대기 중인 진단 기록을 파일로 비웁니다. X의 시간 제한에 따른 강제 종료, 앱 비정상 종료·PC 전원 차단에서는 끝부분 진단이 빠질 수 있습니다. 가능하면 종료 전에 ZIP을 저장하고 재실행 직후 새 ZIP도 저장하세요. 앱이 응답하지 않아 내보낼 수 없으면 해당 실행 폴더의 developer_logs를 사본으로 보존하세요. 새 배포 폴더로 옮기면 이전 폴더의 로그는 새 ZIP에 자동 합쳐지지 않습니다.

진단은 운영 상태와 오류를 기록하며 지정된 패킷 내용 필드는 가립니다. 파일 경로·일반 오류 문자열까지 완전히 익명화하지는 않습니다. 저장 공간·권한·진단 대기열 오류로 일부 기록이 빠질 수 있어 ZIP만으로 모든 조작과 실제 무손실을 증명할 수는 없습니다.

장시간 시험은 구간별 ZIP과 캡처 원본을 따로 남기세요. 이전 0.9.12·0.9.16의 짧은 실사용 표본에서 기록 중 진단 증가량을 환산하면 약 25 MiB는 연속 기록 약 10~20분에 해당합니다. 이 값은 현재 0.9.21의 장시간 실측이나 보장값이 아니며 반복 조작·대상·오류에 따라 더 짧아질 수 있습니다.

화면 응답이 5초 이상 늦어지면 원인 확인용 실행 위치·스레드 스택을 같은 순환 로그에 한 번 기록합니다. 패킷 내용이나 변수 값은 기록하지 않습니다. 응답이 돌아온 뒤 버그리포트를 보내면 멈춘 위치를 확인하는 데 도움이 됩니다.

기본 COM 대상이 RBS 구성의 작성·검증 버전과 다르면 열기에 실패할 수 있습니다. 오류만으로 원인을 단정하지 말고, 현재 기본 CANoe 버전과 RBS에 필요한 버전을 먼저 대조하세요.
