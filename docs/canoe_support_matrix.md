# CANoe 버전·환경별 검증표

0.9.9 현장 추가(2026-10-22): CANoe 19.3.118 /pro에서 CAN+Diag+Zipy 연속 3회와 대상 조합별 총 9구간의 자동 보관을 확인했다. 원래 출력 경로 복구 보류는 0건이었다. 마지막 새 구간은 AppHang 뒤 미완료로 남아 정상 종료/재실행 통과로 처리하지 않는다. 0.9.10의 UI IPC 분리·종료 수정은 실제 재시험 대기다. [근거](capture_fixes_0_9_10.md).

0.9.8 현장 추가(2026-10-22): CANoe 19.3.118 /pro에서 CAN+Zipy 2구간과 CAN+Diag+Zipy 첫 구간의 자동 보관을 확인했다. Diag BLF 13,844 CAN 프레임을 읽었다. Diag 두 번째 prepare는 cfg의 기존 출력 이름 복구 거부로 실패했다. 0.9.9는 같은 경로 거부 대역으로 Diag+Zipy와 세 대상 각각 연속 3구간을 검사하며 실제 새 버전 재시험은 남아 있다. 옵션별 라이선스·VN 상세·차량 무손실은 이 근거로 통과 처리하지 않는다. [근거](canoe_fixes_0_9_9.md).

0.9.8: 0.9.7 현장 3구간에서 정지 후 헤더의 최종 크기/개수 0과 뒤늦은 데이터 추가를 확인했다. 다음 trigger에서 앞 파일을 완성하는 대역과 실제 Runtime CAN+Zipy 3회로 내부 전환·마지막 데이터 보관·번호/측정 유지·정리를 검사한다. 사용자가 현재 실제 시험 불가를 확인해 새 버전 실장 검증은 미수행이다. [근거](canoe_fixes_0_9_8.md).

0.9.7: 0.9.6 현장 리포트에서 선택 trigger 정지·출력 복구 후 파일 핸들 보유와 중첩 번호 오인 차단을 확인했다. 정지한 완전 BLF의 안정된 복사본 보관을 구현하고 실제 Windows 핸들을 유지한 대역·CAN+Zipy 3구간·중단 복구를 검사했다. 실제 두 번째 BLF 9,470프레임은 수동 복구했고, 새 버전의 실장 CAN/Diag 자동 보관·다음 기록은 재시험 대기다. [근거](canoe_fixes_0_9_7.md).

AutoLog 버전별 실제 근거를 관리한다. 이전 버전에서 구성 연결을 확인했어도 새 버전의 실제 기록 성공으로 승계하지 않는다. `대기`와 `확인 불가`는 통과가 아니다.

## 새 시험 결과 추가 규칙

0.9.5 현장 추가: CAN+Zipy가 실제 기록됐고 BLF에서 30,787프레임, PCAP에서 9,597패킷을 읽었다. CAN 정지 후 `_T001` 자동 번호를 외부 변경으로 오인해 보관에 실패했고 기존 복구 기능으로 수동 보관했다. 0.9.6은 지연된 번호 정규화 대역 3구간과 강제 종료 프로세스 검사를 통과했으며 실제 CAN/Diag 자동 보관·연속 기록은 현장 재시험 대기다. [근거](canoe_fixes_0_9_6.md)를 따른다.

- 아래 항목을 회차별 기록하고 위 표에 결과를 추가한다. 업무 cfg 이름·경로·장치 시리얼은 로컬 근거에 두고 Git에서는 별칭을 쓴다.
- AutoLog 버전/소스 커밋, Windows 빌드, CANoe 전체 빌드, 측정 가능한 라이선스 종류와 확인 시각, VN 모델/드라이버, cfg별 논리 CAN 번호→장치 별칭/물리 포트, 블록 이름·출력 형식을 기록한다.
- `연결만`, `실제 기록 통과`, `실패`, `미실행`을 구분한다. 실제 기록 통과에는 시작/정지 3회 이상, BLF 실제 프레임·시간 구간, 측정 유지와 원래 출력 옵션 복구 근거가 필요하다.
- 0패킷 구조 검사 통과나 COM 대역 검사는 실제 CAN 통신 성공으로 등록하지 않는다. 실패는 오류·조작 순서·버그리포트 근거와 함께 남긴다.
- CAN 단독, Diag 단독, 동시 기록의 결과를 각각 기록한다. 하드웨어 기준 일치도 케이블·차량 데이터 수신을 인증하지 않는다.
