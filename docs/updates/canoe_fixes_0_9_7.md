# AutoLog 0.9.7 — 기록 정지와 파일 핸들 보유 구분

> 과거 기록: 이 문서는 작성 당시의 변경·검증 근거를 보존합니다. 현재 동작과 남은 확인 사항은 [현재 구현 상태](../reference/implementation_status.md)를 따릅니다.

2026-10-21. 사용자 제공 리포트를 실제 저장 파일과 대조했다. 개인 경로·원본 캡처·DB는 Git에 포함하지 않는다.

## 확인한 결함

- 리포트 699건, 744,262바이트. ZIP CRC와 manifest의 SHA256 `f1e8dc47fe87188957aa5f91bac4d8d51f41416dd04f72a737a0cad50de094f4` 일치를 확인했다.
- 첫 기록은 CAN trigger가 약 81ms에 정지했고 출력 복구도 성공했다. 그러나 CANoe가 파일 핸들을 유지해 AutoLog의 DELETE 권한·share-mode 0 접근이 WinError 32로 실패했다. 28초 대기와 재시도 끝에도 정지 미확인으로 판단해 다음 기록을 막았다. 핸들 보유만으로 파일이 불완전하다고 단정할 수 없다.
- 두 번째는 약 32ms에 trigger가 정지했지만 원래 `name_T002.blf`에 CANoe가 `_T001`을 덧붙여 `name_T002_T001.blf`가 됐다. 0.9.6의 단일 번호 규칙이 이를 외부 변경으로 잘못 판단했다. 초기 이름은 cfg에서 읽으며 `_T001`로 고정하지 않는다.
- 두 BLF 모두 현재 전체 컨테이너·압축·레코드 구조를 읽을 수 있었다. 첫 파일은 1,382,088바이트, CAN/CAN FD object 45,532개다. 두 번째는 311,948바이트, Python CAN 리더로 9,470프레임·약 2.859초를 읽었다. 두 파일의 선언 object 수와 실제 구조 수는 메타데이터 3개 차이가 나며 기존 검사 정책에 따라 별도로 표시한다. 지금의 정상 파일 상태가 당시 잠금 시점의 header 완결 상태까지 입증하지는 않는다.

## 구현

1. `stop_confirmed`는 선택한 trigger 비활성 확인으로 정의한다. 핸들 보유 때문에 28초 기다리지 않는다. 원래 측정·다른 블록은 그대로 유지한다.
2. 파일 검사는 별도다. 독점 접근이 되면 기존 구조 검사·원자 이동을 사용한다. WinError 32이고 trigger가 비활성이면 고유 작업 폴더에 `.sealed` 복사본을 만든다. 소스의 동일 ID·크기·수정 시각과 두 번 읽은 SHA256이 일치해야 하고, 복사본 전체 BLF header·압축 스트림·객체 경계·선언 개수를 읽어야 보관한다. 잘리거나 변하거나 완결 header가 없는 파일은 통과시키지 않는다. payload는 로그에 남기지 않는다.
3. 봉인 경로와 ID를 보관 전 DB에 기록한다. 보관은 기존 파일을 덮어쓰지 않는 이동이며 정상 보관 후 다음 기록을 허용한다. 이동 직후 DB 커밋 실패/재시작에서도 봉인본·최종본 ID로 복구한다.
4. 잠긴 임시 원본은 유지한다. 이후 구간 보관/다음 실행에서 잠금이 풀리면 소스 ID·크기·전체 SHA256과 최종 보관본 ID가 맞는 것만 독점 핸들로 삭제한다. 다른 내용·사라진/변경된 보관본은 원본을 보존한다. 빈 작업 폴더만 정리한다.
5. 우리 출력 복구가 시작된 같은 cfg·유일한 블록·원래 폴더/이름에서 원래 trigger 증가 옵션에 의한 반복 `_T<숫자>`를 허용한다. 원래 번호의 증가와 뒤에 새 번호가 붙는 경우를 구분한다. 복구 전 외부 경로 수정·수동 활성 trigger·다른 블록/폴더 변경은 계속 차단한다. 임의 필드 코드 전체 지원을 주장하지 않는다.
6. 화면에서 ‘미완료’를 파일 부재로 오해하지 않도록 ‘정지·보관 확인 필요 · 파일 보존’과 설명을 세 언어로 표시한다. X 강제 종료 정책은 유지한다.

## 현장 파일 정리

AutoLog 프로세스가 실행 중이지 않은 것을 확인하고 SQLite 사전 백업을 만들었다. 두 번째 BLF를 기존 RecoveryService로 최종 저장 폴더에 보관했고 원문 SHA256 `ac0d1c6fdded5163e3b4cadced3e4470da345785d08ce866d894121c7aa7ca13` 일치를 확인했다. 해당 기록만 수동 검토 완료 처리해 실패 이력·PCAP·다음 번호 669를 보존했다. CANoe 창/측정은 조작하지 않았다. 근거와 사전 DB 백업은 로컬 빌드 저장소 `field-recovery-0.9.7/`에 보관한다.

## 검증 범위

Windows의 실제 읽기/쓰기 핸들을 연 상태에서 복사·보관·핸들 해제 후 정리, 복사 중 변경·불완전 header·충돌·다른 경로·변경/누락 보관본 보존, 중첩 번호·임의 초기 이름·3구간, CAN+Zipy 3회 정상 완료, 봉인 이동 전후 중단 복구를 검사한다. 실제 CANoe의 새 버전에서 시작→정지→자동 보관→다음 기록을 재시험해야 한다. 당시 핸들 유지 중 완전한 BLF가 실제로 읽혔는지는 이 리포트만으로 확정할 수 없으므로 재시험 로그에 `canoe.snapshot_sealed` 또는 파일 완결 검사 실패 근거를 남긴다.

전체 자동 검사 545개(56.25초), Ruff·의존성·diff·문서 로컬 링크 266개 검사를 통과했다. 정지 직후 완결 header가 늦게 반영되는 경우는 최대 2초 동안 실제 파일 검사만 재시도하며 핸들 해제를 기다리지는 않는다. 미완결 상태 지속 거부와 실패 시 파일의 실제/선언 크기 진단도 검사했다. 가이드 개정 2026-10-21.4는 PC/작은 폭 8개 뷰포트로 렌더링하고 기록 절차 화면을 확인했다.

공식 근거: Vector의 [Trigger](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/Objects/COMObjectTrigger.htm)는 비활성을 기록 정지로 설명하며, [Logging](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/Objects/COMObjectLogging.htm)은 파일명 설정을 제공하지만 일반적인 강제 파일 핸들 닫기/Flush를 제공하지 않는다. 모든 파일 핸들 해제를 필수 정지 조건으로 삼은 것은 AutoLog의 구현 선택이었다.
