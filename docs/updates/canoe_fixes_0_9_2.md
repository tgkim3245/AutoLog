# AutoLog 0.9.2 — CANoe 로그 시작·출력 복구 차단 수정

> 과거 기록: 이 문서는 작성 당시의 변경·검증 근거를 보존합니다. 현재 동작과 남은 확인 사항은 [현재 구현 상태](../reference/implementation_status.md)를 따릅니다.

2026-10-20 · 수동 기록은 되지만 AutoLog에서 시작되지 않는 현장 오류를 수정했다. 새 EXE의 실제 CAN/Diag 장비 재시험은 남아 있다.

## 현장 근거

리포트의 ZIP CRC와 manifest의 크기/SHA256을 검증했다. 개발자로그 432개 레코드, 609,497바이트이며 SHA256은 `08242b63e41febd7fc863445a6499c88531163223817af876c4685fb5975ba47`이다. 원본 리포트·업무 프로젝트·개인 경로는 Git에 넣지 않는다.

- 선택 대상은 CAN cfg의 **1번 `CAN_Logging` BLF**다. 2번 `ETH_Logging` PCAPNG를 CAN 대상으로 선택한 것이 아니다.
- 사용자가 수동 로깅 성공을 확인했고, 10:36:11 연결 재확인에서는 **측정 실행 중·선택 trigger 정지**를 관측했다. 이전 측정 대기 상태에서 수동 출력 경로 변경 뒤 발생한 선택 검증 오류는 명시적 재연결로 해소됐다.
- 10:36:16 prepare는 통과했다. 10:36:17 configure에서 AutoLog가 `.vil_work/<세션>/prefix_500.blf`로 경로를 적용하고 `IncrementAfterTrigger`를 껐다. 이후 `_validate()`가 COM identity 차이를 다른 블록으로 판단해 실패했다. 로그에는 요청한 경로와 옵션이 실제 반영돼 있다.
- 같은 검사 때문에 원래 출력 복구와 이후 연결 확인까지 반복 실패했다. **CAN trigger Start 명령은 호출되지 않았다.** 이번 시작 실패를 라이선스·채널 매핑 오류로 설명하지 않는다.
- XL DLL 조회는 별도로 확인 불가였으나 저장한 하드웨어 기준이 없어 이 시도의 차단 원인이 아니었다. 실제 VN 모델·시리얼/포트 조회 성공은 확인하지 못했다.

## 사진의 Logging 패널과 AutoLog 대상

대표 프로젝트의 `Panels/Logging.xvp`에서 버튼은 `Logging::logging_btn`에 연결돼 있다. `CAPL/logging.can`은 이 변수를 받아 `startLogging()`/`stopLogging()`을 호출하고 별도 `logging_sta` 상태와 버튼 배경색을 바꾼다. cfg가 이 패널과 CAPL 파일을 참조하는 것도 읽기 확인했다.

AutoLog는 이 패널을 클릭하거나 해당 시스템 변수를 바꾸지 않는다. 선택한 BLF 블록의 `Trigger.Start/Stop`을 직접 호출한다. 따라서 패널의 이름이 `Logging`이고 실제 대상 블록 이름이 `CAN_Logging`이어도 연결이 잘못됐다는 뜻은 아니다. 패널의 배경색/내부 토글은 AutoLog의 기록 증거가 아니며 기록 중 두 제어를 함께 사용하지 않는다. AutoLog의 시작 증거는 선택 trigger 활성과 정확한 파일 경로의 BLF 헤더다.

## 구현 수정

0.9.1은 대기 중에만 새 COM identity를 허용했다. 실제 CANoe는 출력 적용·기록·복구 때도 조회마다 새 인터페이스를 반환할 수 있어 이 정책은 동작을 막는다. IUnknown 비교도 논리 블록의 영구 ID를 대신할 수 없다.

- **모든 단계에서 논리 선택 검증**: cfg 전체 경로, 선택 인덱스, 전체 블록 개수/순서·이름과 출력 경로를 재조회한다. 동일 이름·정규화 경로의 후보가 둘이면 모호한 선택으로 차단한다. Python/IDispatch/IUnknown 객체 주소를 비교하지 않고 검증한 현재 객체를 사용한다.
- **변경 가능한 출력과 블록 구분**: 대기 중에는 확인했던 블록 경로, 출력 적용/복구 중에는 원래 경로 또는 이번 세션 경로만 허용한다. 다른 블록의 경로와 순서/이름 변경도 차단한다. 임의 외부 경로는 복구로 덮어쓰지 않는다.
- **단계별 소유권 조건 유지**: configure가 정확한 새 BLF 경로·자동 분할 꺼짐·측정 실행을 확인한다. Start/query는 정확한 세션 출력 경로와 분할 꺼짐을 확인한다. Stop도 세션과 정확한 출력 경로가 맞아야 trigger를 정지한다. 복구는 trigger 정지와 모든 파일 옵션의 충돌 여부를 확인한 뒤 원래 경로·옵션으로 되돌린다. 부분 COM setter 실패 후 복구 재시도도 허용한다.
- **진단**: stats와 출력 적용 성공에 논리 선택/소유 경로 검증 방식을 기록한다. 실패 시 기대/허용 경로와 실제 블록 목록이 남는다. 조회 성공마다 장황한 로그를 추가하지 않는다.

완전히 동일한 이름/순서/출력 상태로 블록을 삭제·재생성하면 영구 ID가 없는 API에서 이를 별도 물리 객체로 구분할 수 없다. 같은 논리 대상으로 취급하며, 출력 소유 중에는 고유 세션 경로와 단계별 조건을 추가로 확인한다. CANoe의 측정/원본 cfg/라이선스/매핑은 자동 변경하지 않는다.

## 검증

- 매 `LoggingCollection.Item()`에서 서로 다른 프록시와 IUnknown을 반환하되 같은 내부 블록을 제어하는 대역을 만들었다. **기존 0.9.1 소스에서 같은 `Logging block changed` 오류를 재현**했으며 새 소스에서는 3구간의 configure/start/query/stop/BLF 구조 검사·원래 경로/옵션 복구를 통과했다. 다른 블록 trigger와 원본 cfg는 유지했다.
- 프록시가 달라지는 상태에서 외부 cfg/블록/이름/경로/순서/개수/중복 변경의 차단, 외부 편집 보존, 시작 전 취소, 부분 파일 옵션 setter 실패의 원복을 검사했다. 객체 주소 자체의 변경을 차단해야 한다던 이전 검사는 실제 논리 선택 변경 검사와 새 프록시 정상 동작 검사로 교체했다.
- 전체 자동 검사 **471개 통과(30.30초)**, Ruff·pip 의존성·diff 공백 검사 통과. 실제 CANoe 활성화·장비 측정·원본 프로젝트 수정은 수행하지 않았다.
- 구버전 실패 재현과 원본 ZIP 무결성 결과는 로컬 `Downloads/AutoLog_Builds/canoe-fixes-0.9.2/regression_result.json`에 보관했다. 대역의 BLF 구조 검사는 실제 CAN 데이터 수신을 인증하지 않는다.

## 기존 0.9.1에서 실패한 뒤 재시험

0.9.1은 복구도 차단했으므로 열린 CANoe의 BLF 출력 경로가 `.vil_work`에 남아 있을 수 있다. 구버전에서 수동 버튼으로 추가 기록하기 전에 해당 출력 설정을 확인한다. 수동 기록을 끝내고 필요한 작업/파일을 확인한 뒤 기존 AutoLog와 전용 CANoe 창을 정리하고, 0.9.2에서 cfg를 새로 열어 준비한다. 임시 출력 경로를 원본 cfg에 의도치 않게 저장하지 않도록 확인한다.

구버전이 출력 복구 오류 때문에 X 종료를 계속 보류하면, 수동 기록과 AutoLog 기록이 모두 정지한 것을 직접 확인한 뒤 작업 관리자에서 구버전 AutoLog를 종료해야 할 수 있다. 이는 구버전 교체 절차이며 새 버전이 실행 중인 이전 프로세스를 자동 종료하거나 해당 CANoe를 임의 인수하지 않는다.

재시험은 **cfg별 연결 확인 → 전용 CANoe에서 F9/Trace 확인 → AutoLog 연결 재확인 → AutoLog logging 시작/정지**로 한다. 패널 버튼은 함께 사용하지 않는다. [현장 체크리스트](../testing/licensed_canoe_validation.md)에 실제 BLF 구간과 측정 유지·원래 설정 복구 결과를 기록한다.

- 빌드 PC의 XL DLL 미발견은 기존과 같으며 이번 버전에서 드라이버 검색/하드웨어 기준 정책을 바꾸지 않았다. 실제 장비 재시험은 수행하지 않았다.
