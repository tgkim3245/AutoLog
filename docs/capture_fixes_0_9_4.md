# AutoLog 0.9.4 — CAN 정지 지연·연속 기록과 네트워크 선택 수정

2026-10-20. 0.9.3 현장 리포트에서 CAN+Zipy 시작 성공과 CAN 종료 실패를 확인했다. 0.9.4의 실제 CANoe 장비 재시험은 아직 수행하지 않았다.

## 리포트에서 확인한 사실

ZIP CRC와 manifest 크기/SHA256을 확인했다. JSONL 1,459개 레코드, 1,352,502바이트, SHA256 `c018644bc8e9011a43a1ecbaf66cc08c40b1cb7ee605d1843dc277a1c00f905e`이다. 원본 로그·cfg·개인 경로·장치 식별자는 Git에 넣지 않는다.

- CAN의 `CAN_Logging` BLF 블록과 Zipy 모두 prepare/configure/start에 성공했다. CAN은 실제 trigger 활성·정확한 작업 경로의 BLF 헤더까지 확인했다. 이전 리포트의 시작 전 블록 검사 오류와 다르다.
- 한국 시각 18:17:30.621에 양쪽 정지 요청을 보냈다. Zipy는 18:17:30.979에 정상 정지했다(약 0.36초).
- CAN은 18:17:58.719에 약 28.10초 후 실패했다. 관측된 trigger는 비활성이고 측정은 실행 중이었으나 작업 BLF에 대한 독점 접근이 WinError 32로 거부됐다. 시작 전 출력 경로·옵션 복구도 남아 있었다.
- 제어기는 양쪽 정지 결과를 받은 뒤 파일 검사로 진행했다. Zipy의 24바이트 PCAP은 구조 검사에 통과했으나 **0패킷**이다. 차량 수신 성공 근거는 아니다.
- 세션이 미완료로 남아 새 기록을 막았다. 다음 start 명령 실패가 추가로 발생한 것은 아니다.
- 네트워크 선택 저장 95회와 잦은 재조회가 관측됐다. 실제 Qt 마우스 시험으로 클릭한 항목이 선택되지 않는 결함을 별도로 재현했다.

## CAN 정지 처리 수정

기존 순서는 `Trigger.Stop → 작업 파일 독점 접근 대기 → 원래 출력 복구`였다. trigger를 멈춘 뒤에도 CANoe가 현재 출력의 파일 핸들을 보유한다면 경로 복구 전에 28초가 지나 실패하고, 다음 기록도 계속 막힌다.

0.9.4는 `Trigger.Stop → 비활성 확인 → 원래 출력 경로·옵션 복구 → 작업 BLF 독점 접근 → 구조 검사·보관` 순서다. 별도 `trigger_stopped`와 `stop_confirmed`로 기록 정지와 파일 닫힘을 구분한다. 정상적으로 닫히면 불필요한 고정 대기는 없다. 실제 파일 잠금·후행 쓰기가 지속되면 기존 대기 한도와 미완료 처리를 유지한다.

정지 후 경로를 복구했어도 닫힘 미확인이면 새 configure를 거부한다. 정지 재시도 사이 다른 수동 기록이 시작되면 이를 대신 정지하거나 출력 경로를 덮어쓰지 않는다. 복구 오류와 파일 닫힘 확인 결과를 별도로 보존한다. CANoe 측정·창은 정지하지 않는다.

`canoe.trigger_stopped`, `canoe.file_close_waiting`, `canoe.segment_closed`에 상태·대기 원인·소요 시간을 남겨 다음 현장 리포트에서 구간을 구분한다.

**확인 범위:** 로그는 잠긴 파일의 소유 프로세스를 알려주지 않는다. 경로 복구가 실제 CANoe의 핸들을 해제하는지는 현장 재시험이 필요하다. 대역은 trigger 정지 후 실제 Windows 파일 핸들을 유지하고 경로 변경 시 닫도록 구성했으며, 기존 코드의 동일한 28초/WinError 32 실패와 수정 코드의 3회 연속 완료를 비교했다. 실제 CANoe에서 성공했다고 표현하지 않는다.

참고한 Vector 공식 [Logging 객체](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/Objects/COMObjectLogging.htm)와 [Trigger 객체](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/Objects/COMObjectTrigger.htm), 설치된 CANoe 19 타입 정보에는 별도 Close/Flush 메서드가 없다. Trigger.Active의 비활성은 파일 핸들 닫힘의 보증으로 사용하지 않는다.

## 네트워크 클릭 선택 수정

Qt가 항목의 선택을 확정하기 전에 popup 닫힘 콜백에서 clear/addItem으로 모델을 다시 만들었다. 클릭한 QModelIndex가 무효화돼 선택이 취소되거나 저장이 반복될 수 있었다.

목록을 닫는 콜백을 queued connection으로 처리해 Qt의 선택 확정·설정 저장 뒤에 대기 중인 목록을 반영한다. 드롭다운을 연 상태에서는 모델을 유지하고 그래프만 갱신한다. 마우스와 키보드 선택 중 장치 순서가 바뀐 재조회가 도착해도 선택 NIC가 유지되고 한 번만 저장되는지 검사했다.

## X 종료 수정 (2026-10-21)

추가 사용자 제보에 따라 두 결함을 회귀 검사로 재현했다. 이전 실행의 미완료 세션만 있어도 종료를 막던 조건과, 종료 중 예기치 않은 정지 예외가 `exit_ready` 응답을 누락해 이후 X 클릭을 무시하게 만드는 경로다. 제보 당시의 새 종료 로그가 없으므로 두 결함 중 어느 것이 해당 실행의 원인인지는 단정하지 않는다. 기존 리포트의 현재 CAN 정지 미확인도 종료를 보류하는 조건이다.

이전 세션은 파일·이력·번호를 보존하고 정상 종료하며 복구 전 새 캡처 차단은 유지한다. 현재 세션 정리 예외는 미완료로 보존하고 반드시 종료 실패 응답과 재시도 가능 상태로 복귀한다. 종료 보류 시 한국어·영어·중국어 안내를 표시한다. 실제 정지 미확인 상태를 성공으로 바꾸거나 기록 프로세스를 강제 종료하지 않는다.

회귀 검사는 이전 미완료를 두 번 재실행해 보존/종료 확인, 정지 예외 후 재시도·파일 보관 확인, 실제 Qt 창 닫기 이벤트의 이전 이력 종료와 예외 후 안내·재종료 두 경우를 포함한다.

## 현장 재시험

자동 검사 500개와 Ruff·의존성·diff 검사를 통과했다. 전체 실행의 UI 시험 1개에서 초기화 완료 전 상태를 읽는 시험 코드 경합을 수정한 뒤 해당 UI·배포 문서 검사 11개를 다시 통과했다. 실제 CANoe의 구간 완결은 대역 검사와 구분한다.

1. 기존 기록·미완료를 정리하고 기존 앱을 종료한 뒤 새 폴더의 0.9.4를 실행한다.
2. 네트워크를 클릭해 선택한 이름이 유지되는지 확인한다.
3. CAN+Zipy로 짧은 기록을 시작·정지하고 보관 완료까지의 시간을 확인한다. 3회 반복해 다음 기록이 가능한지 확인한다.
4. 매회 CANoe 측정 유지, 원래 BLF 출력/옵션 복구, 최종 BLF 실제 프레임·PCAP 수신 내용을 확인한다.
5. 미완료가 남으면 정지 재시도 후 버그리포트를 보낸다. 정리 전 임시 파일을 삭제하지 않는다.
