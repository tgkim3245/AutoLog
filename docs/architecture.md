# 통합 제어 설계

최신 현황(2026-10-20, 0.9.4): Qt 앱, 대상별 worker, SQLite 설정/번호/이력, dumpcap 원본 취득·독립 TShark 해석·감시·품질, 파일 관리·수동 복구, CAN/Diag 독립 연결과 준비 상태/로컬 채널 기준 비교가 구현되어 있다. 개발자로그는 EXE 옆에서 순환 저장하고 버그리포트 ZIP으로 내보낸다. CANoe 블록은 COM 객체 주소 대신 cfg·논리 선택·소유 출력 경로로 모든 구간 단계에서 검증한다. 수동 시험 후 정지한 동일 BLF 블록의 파일명 변경은 출력 소유 전에만 재조회한다. 최신 수정은 [0.9.4 종료·네트워크 선택 수정](capture_fixes_0_9_4.md), 이전 [0.9.3](canoe_fixes_0_9_3.md), 기능 범위는 [0.9.0 변경](usability_update_0_9_0.md)을 따른다.

현재 요구사항: 55개, 검증 시나리오 66개. 아래 설계 전체의 완료를 뜻하지 않는다. 라이선스가 필요한 CAN/Diag 구간 BLF·수신/채널 감시, 차량 고부하·장시간·새 PC 시험은 남아 있다. 상세 동작은 [제어 정책](control_policy.md), 검증은 [검증 계획](validation_plan.md), 진행은 [구현 계획](implementation_plan.md)을 따른다.

## 1. 구성과 책임

    작은 통합 패널
        │ 명령 / 대상별 실제 상태 / 파일명 / 알림
    세션 제어기 ── 영구 상태 저장소
        ├─ CANoe 1 전용 실행부
        ├─ CANoe 2 전용 실행부
        └─ Ethernet 실행부
                ├─ 원본 파일
                ├─ 패킷 요약 → 감시
                └─ 최근 목록 → 패킷 보기 창

화면은 외부 도구를 직접 제어하지 않는다. 세션 제어기가 준비 검사·번호 예약·시작·정지·부분 실패·파일 보관을 관리한다. 대상별 실행부는 명시적 Start/Stop/Query와 세션·명령·대상 세대 식별자를 사용한다.

COM 호출·외부 출력 소비·파일 검사를 UI 스레드에서 기다리지 않는다. 한 대상이 응답하지 않아도 다른 대상의 상태 표시·정지 요청은 처리할 수 있어야 한다. 시간 초과가 실제 기록 정지를 의미하지는 않는다.

## 2. CANoe 실행과 사용자 편집

사용자가 CANoe 1·2에 .cfg 전체 경로를 지정한다. 통합 프로그램이 생성한 대상과 실제 제어 참조를 대응시키고 로드한 구성·기록 블록을 확인한다. 이미 열린 무관한 창 연결은 제외한다.

사용자가 CANoe 화면에서 설정을 수정·저장하고 측정을 시작한다. 패널은 측정을 유지한 채 구간 기록만 제어한다. 이번 세션의 출력 경로·이름은 기록 정지 상태에서 패널이 적용하고 다시 읽어 확인한다. 그 외 사용자 설정을 복원하거나 원본 .cfg를 자동 저장·재로드하지 않는다.

같은 슬롯의 같은 구성은 중복 실행하지 않는다. 다른 구성으로 바꾸려면 해당 측정·기록이 정지돼 있어야 한다. 미저장 변경은 CANoe의 사용자 확인 절차를 따른다. 사용자가 외부에서 프로젝트를 교체하면 기존 참조를 무효화한다.

Logging/Trigger COM 제어를 구현했다. CANoe 19.3.118에서 다른 PID·정확한 cfg의 독립 연결은 확인했다. 측정 유지 중 파일명/옵션 적용·구간 완결·복구는 라이선스 활성 상태에서 실증해야 한다. CAPL 수정·추가는 수행하지 않았으며 원본 cfg를 자동 저장하지 않는다. SingleCOMClient=1은 원본 can.ini 백업 후 자동 준비하고 공유 창으로 대체 연결하지 않는다.

근거: [CANoe 19 COM](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/COMInterface.htm), [Logging](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/Objects/COMObjectLogging.htm), [Trigger](https://help.vector.com/CANoeDEFamily/19/en/Help/Content/Topics/COMInterface/Objects/COMObjectTrigger.htm).

0.9.4의 정지는 trigger 비활성 확인→시작 전 출력/옵션 복구→작업 BLF 독점 접근 순서다. `trigger_stopped`는 `stop_confirmed`와 별개이며 경로 복구만으로 세션 완료를 인정하지 않는다. 닫힘 미확인 상태는 새 configure를 막고, 재시도 중 다른 수동 trigger가 활성화되면 이를 정지하지 않는다. 파일 닫힘 이후 구조 검사·보관을 수행한다.

## 3. Ethernet 캡처·패킷 목록

사용자 확인 범위는 출처·목적지·프로토콜·수신 시각과 최근 목록으로 확정했다. 작은 메인 창에서 별도 패킷 보기 창을 열고 표시 일시 정지·필터·창 닫기는 원본 기록과 감시에서 분리한다.

0.9.0에서는 dumpcap이 NIC에서 원본 파일을 직접 기록한다. 별도 TShark는 표준입력으로 전달된 같은 파일의 증가분을 해석한다. 후행 읽기는 최대 64 KiB씩 전달하며 파이프가 막히면 후행 스레드만 대기한다. 원본 쓰기는 이 파이프를 거치지 않는다. 해석 실패는 감시 확인 불가/해석 오류로 남기고 원본 취득을 유지한다. 정지 시 원본 정상 닫힘을 확인한 뒤 해석을 최대 5초 배출하고, 지연된 읽기 전용 해석 프로세스는 정리할 수 있다. 원본 기록 프로세스 강제 종료는 정상 정지로 취급하지 않는다. 별도 Wireshark GUI 제어는 제공하지 않는다.

톱니바퀴 설정에서 NIC 한 개를 안정적인 식별자로 선택하고 Wireshark 연결 준비를 확인한다. CAN·Diag의 cfg·기존 BLF 블록 선택도 설정창에서 수행한다. 연결 조작은 취득을 시작하지 않는다. 실제 NIC 열기·기록 준비는 세션 시작에서 확인한다. 사용자 화면 표기는 CAN=CANoe 1, Diag=CANoe 2, Zipy=Wireshark 캡처 대상이다. 메인 창은 세 대상을 기본 480px 폭의 가로 카드로 보여주고 작은 화면에서는 폭/높이를 제한하고 스크롤한다. 선택·상태·공통 logging 버튼과 알림 로그를 유지한다. Ethernet 확장자 선택은 설정창에서 한다. 연결 상태는 메인과 설정창에서 함께 확인한다. 프로세스 생존·단일 시작 문구·파일 존재만으로 취득 성공이나 통신 정상을 단정하지 않는다.

pcap/pcapng 실제 출력 형식을 지정하고 결과를 확인한다. 표시/감시 조건으로 원본 캡처를 제한하지 않는다. 표준출력·오류출력을 지속 소비하고 숨김 실행부에서 검증된 정상 정지 수단을 사용한다. 강제 종료를 정상 정지로 사용하지 않는다.

최근 1,000건, 화면 반영 약 250ms를 초기 표시 설정으로 둔다. 감시는 화면 버퍼 밖의 수신 정보에서 처리한다. 해석 지연·누락을 확인 불가로 표시하며 UI와 실행부를 분리했다는 사실만으로 원본 취득 성능이 보장된다고 보지 않는다.

근거: [TShark](https://www.wireshark.org/docs/man-pages/tshark.html), [dumpcap](https://www.wireshark.org/docs/man-pages/dumpcap.html), [Windows 콘솔 이벤트](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent).

## 5. 시작·중단·종료

### 시작

1. 설정에서 prefix·다음 인덱스를 적용할 때 선택 대상의 예상 파일명을 저장 폴더의 기존 파일과 비교해 충돌을 알린다. 시작 직전 실제 파일 시스템에서 대상·구성·블록·측정·도구/NIC·경로·파일명·쓰기 가능 여부를 다시 확인한다.
2. 실제 채널 매핑 불일치는 차단한다. 매핑 취득 불가만으로는 정상으로 간주하지 않고 경고를 유지하며, 다른 기록 준비가 확인되면 취득을 허용한다.
3. 고유 임시 경로를 준비하고 출력 적용을 확인한다. 사전 준비 실패·이름 충돌이면 기존 파일을 보존하고 번호를 예약하지 않는다.
4. 고유 세션 ID·선택 대상·임시/최종 파일·예약 번호·다음 번호를 트랜잭션으로 영구 저장한다. 실패하면 외부 기록 명령을 보내지 않는다.
5. Ethernet을 선택했으면 그 기록 준비를 먼저 확인하고 CANoe 구간 기록을 요청한다. 선택하지 않은 대상에는 기록 명령을 보내지 않는다.
6. 모두 시작 확인되면 기록 중으로 전환한다. 시작 단계 실패·시작 취소는 이번 요청이 새로 시작한 구간만 정리한다. 측정과 부분 파일을 유지하고 번호를 자동 되돌리지 않는다.

### 기록 도중

한 대상이 중단되면 오류와 세션 부분 실패를 표시하고 나머지는 계속 기록한다. 실패 대상을 같은 세션에 자동 재시작하지 않는다. logging 버튼은 남은 대상의 정지로 동작한다.

선택한 대상의 실제 기록 중에만 통신 감시를 수행한다. 미수신·출처 불일치·기준 미설정은 기록 자동 정지 사유가 아니다. 도구·파일 상태 확인은 준비와 종료 때도 유지한다.

### 정지

1. 종료 처리로 전환하고 중복 시작·설정 변경·파일 관리를 막는다.
2. 이번 세션의 모든 남은 기록에 정상 정지를 요청한다. CANoe 측정·창·다른 블록은 유지한다.
3. 후행 기록·파일 닫힘·쓰기 완료를 대상별 확인한다. 시간 초과·확인 불가는 미완료로 남긴다.
4. 종료 확인된 파일을 검사하고 최종 경로로 교체 없이 보관한다. 파일별 결과·실제 경로를 저장한다.
5. 일부 중단·누락·보관 실패가 있으면 전체 성공으로 표시하지 않는다. 유효한 빈 파일과 기대 데이터 수신 여부도 구분한다.

초기 작업 제한·시작 중 취소·늦은 응답 처리는 제어 정책을 따른다. 정확한 취득 시각 동기화는 보장하지 않으며 요청·시작 확인·파일 내부 시간 기준을 구분한다.

## 6. 파일 저장·영구 상태

    지정한 공통 저장 폴더/
    ├─ .vil_work/고유 세션 ID/
    │   ├─ AutoLog_7.blf
    │   ├─ AutoLog_Diag_7.blf
    │   └─ AutoLog_7.pcap
    ├─ AutoLog_6.blf
    └─ AutoLog_6.pcap

기록 중 기본 이름·확장자는 최종 이름과 같고 임시 폴더만 다르다. 실제 경로·저장 중/보관 완료/미완료를 화면에서 확인할 수 있다. 닫힘·읽기 확인 후 공통 폴더 루트로 이동하며 최종 이름이 있으면 기존 파일과 임시 파일을 모두 보존한다.

세션·번호·설정·파일별 결과·이벤트는 Windows 사용자별 로컬 SQLite 저장소로 관리한다. 앱은 사용자 세션당 한 개만 실행한다. 파일 일련번호와 내부 세션 ID를 구분하고 명시적 번호 변경도 허용한다.

이름 변경·삭제는 활성 기록/종료/확인 불가가 정리된 뒤 보관 완료 파일만 대상으로 한다. 여러 파일 작업의 일부 실패를 기록하고 실제 경로를 회수한다. 강제 잠금 해제·외부 프로그램 종료는 사용하지 않는다. 외부 앱의 모든 파일 사용 여부를 탐지한다고 보장하지 않는다.

## 7. 화면·이력·창 종료

메인은 세 대상 카드·전체 파일명·저장 폴더·logging·알림과 직전 로그 이름 변경/삭제 동작을 담는다. 이름 변경은 메인에 고정 노출된 텍스트박스와 버튼으로 수행해 조작에 따라 창이 확장되지 않는다. prefix·다음 인덱스·공통 저장 폴더 설정은 톱니바퀴 설정창에서 관리한다.

이벤트는 코드·파라미터·시각·대상·등급·원문으로 저장한다. 화면의 앱 설명은 한국어/영어로 전환하고 외부 원문·경로는 보존한다. 메인 최근 500건은 내부 스크롤로 표시하고 중요 동작 이력은 디스크에 보관한다.

개발자로그는 상시 켜고 `vil_logging.*` 진단을 JSONL로 저장한다. 배포판에서는 EXE와 같은 배포 폴더의 `developer_logs`에 두며 5MB 파일과 최대 4개 백업으로 회전한다. 유한 큐로 기록을 전달하고 종료 시 큐를 비운 뒤 flush/close한다. 메인의 버그리포트 버튼은 해당 로그를 ZIP으로 내보낸다.

명령 요청/응답·세션/대상/명령 ID·상태 전이·경과시간·오류 원문/traceback·앱/도구 버전과 진단 확인 범위를 남긴다. 파일/큐 오류는 별도로 보고하고 기록 제어 경로로 전파해 실제 취득을 중단하지 않는다. 화면은 경로와 폴더 열기를 제공하고 사용자가 파일을 직접 전달한다. 자동 업로드와 캡처 payload 저장은 하지 않는다. 실제 Ethernet·독립 CANoe 연결 진단도 확인했다. 라이선스 CAN 구간 기록의 진단은 현장 시험으로 추가 확인한다.

메인 창 X와 명시적 종료는 기록 정리와 파일 확인을 마친 뒤 종료한다. 종료 확인 실패 시 미완료 상태를 알리고 창을 유지한다. CANoe 측정·창을 자동 종료하지 않는다.

비정상 종료 후 미완료 세션·예약 번호·실제 파일을 회수한다. 이전 CANoe로 자동 연결하거나 미완료 파일을 성공으로 승격하지 않는다. 남은 기록 가능성은 사용자 확인이 필요한 상태로 표시한다.

## 8. 다른 시험 PC에서의 실증

실제 도구 경로·버전·드라이버·권한·채널/NIC를 PC 설정으로 분리한다. 개발 PC 경로를 코드에 넣지 않는다.

본구현의 주요 실증 조건은 두 CANoe의 독립 제어, 측정 유지 중 구간 파일 완결, TShark 저장과 필드 출력·0패킷 준비·정상 정지·실제 부하다. 감시 수신 근거와 장비/채널 정보도 실제 지원 범위를 확인한다.

장비 없는 세션/파일/상태 검증과 실제 도구·장비 검증을 구분한다. CAPL 추가 허용 여부·소스·주기·미수신 임계값은 미확정 상태다. 차량·장비 상태 변경을 일반 자동 검사에 포함하지 않는다.

현재 HTML은 기존 시안으로 유지한다. Python 앱은 Qt 화면·대상별 모의 실행부·SQLite·로컬 진단 기반을 구현했다. 이 문서의 실제 도구·파일 보관·감시 설계 전체가 구현됐거나 실증됐다는 의미는 아니며, 단계별 사실은 [1단계 개발 결과](development_stage_1.md)에 기록한다.

## 구현 언어와 배포 기준

2026-10-17 설계 선택: Python + PySide6(Qt Widgets)를 기준으로 구현한다.

| 역할 | 선택 |
| --- | --- |
| 화면·설정·최근 패킷 목록 | PySide6 Qt Widgets |
| 세션 제어·파일 관리·이벤트 | Python |
| CANoe 자동화 연결 | pywin32의 Windows COM 지원. 두 대상의 독립 참조는 별도 실증 |
| Ethernet 원본 취득·요약 | 설치된 Wireshark의 TShark |
| 번호·세션·이력 보존 | Python 표준 sqlite3 / SQLite |
| Windows 배포 | PyInstaller의 실행 파일 포함 폴더 배포를 우선 검증 |

이 도구는 로컬 Windows 데스크톱 프로그램으로 만든다. 기존 HTML은 화면 시안이며 실제 화면은 Qt Widgets로 구현한다. Python·라이브러리 버전은 시험 PC의 Windows·CANoe 연동과 패키징을 확인한 조합으로 고정한다.

Python 런타임과 사용 라이브러리를 배포물에 포함해 시험 PC에서 Python을 별도 설치하지 않고 실행할 수 있게 한다. CANoe 19·라이선스·Wireshark/TShark·캡처/장비 드라이버는 시험 PC의 외부 실행 환경이다. 이를 통합 프로그램이 함께 설치하는 기능은 포함하지 않는다.

처음에는 실행 파일과 의존 파일을 담은 폴더 배포로 검증한다. 단일 파일 EXE 여부는 필수 요구가 아니며 설치 환경과 실제 실행 결과에 따라 결정한다. UI와 도구별 실행부 분리, 출력 소비, 정상 종료·파일 보관 규칙은 그대로 적용한다.

CAPL은 필요한 CANoe 내부 보조에 한정해 검토하며 통합 프로그램 전체를 작성하는 언어로 사용하지 않는다. 언어 선택으로 미검증 CANoe API·복수 제어·TShark 성능 문제가 해결됐다고 보지 않는다.

근거: [Qt for Python](https://doc.qt.io/qtforpython-6/), [pywin32](https://github.com/mhammond/pywin32), [Python sqlite3](https://docs.python.org/3/library/sqlite3.html), [PyInstaller 배포](https://pyinstaller.org/en/stable/operating-mode.html).

## 개발 착수·운영 환경 보완

현재 사용자 확인 환경은 Windows 11 64비트, 팀 여러 PC, 로컬 디스크, 약 1분의 일반 구간과 30분 초과/1GB 초과 가능 로그다. 사용자는 VN 장비를 연결해 CANoe 라이선스를 인증한다.

앱은 오프라인으로 실행하며 외부 API·로그인·자동 전송·자동 업데이트·실행 중 다운로드를 사용하지 않는다. TShark 이름 해석을 끄고 설치 때 준비한 로컬 도구를 사용한다. 차량용 NIC와 VN 장비는 해당 취득에 필요하다.

기존 .cfg는 되도록 유지한다. CAPL·시스템 변수 정의를 자동 추가하지 않고 원본 .cfg/관련 소스를 자동 저장하지 않는다. 세션 출력 경로는 실행 중 해당 블록 설정에 적용할 수 있으나, 사용자 직접 저장이 없는 조건에서 원본 파일 보존을 실증한다. COM/기존 관측값으로 얻지 못하는 감시는 미지원/확인 불가로 표시하고 프로젝트 복사본 보조안은 별도로 검토한다.

Windows용 배포 폴더와 PC 프로필·번호 DB·실제 로그를 분리한다. 앱 교체로 로컬 상태를 덮어쓰지 않으며 실제 EXE에서 외부 도구의 DLL 검색·작업 프로세스·정상 정지를 확인한다. 대용량 파일 검사와 보관은 진행 상태를 표시하고 원본 취득 정지 시간 제한과 검사 시간 제한을 구분한다.
