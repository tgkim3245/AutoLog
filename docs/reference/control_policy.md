# 현재 제어 정책

기준 SW 1.0.0 · 코드 대조 2026-10-25

이 문서는 `runtime.py`, CANoe/TShark 어댑터, 저장·종료 코드의 현재 동작을 설명한다. 초기 제안의 120/15/30초 제한이나 한쪽 실패 후 계속 기록 정책을 현재 사양으로 사용하지 않는다. 구현 구조는 [설계](architecture.md), 재현 절차는 [실차 TC](../testing/vehicle_test_plan.md)를 따른다.

## 준비와 번호 예약

1. 저장 위치·선택 역할·cfg·BLF 블록·NIC·도구 설정을 검사한다. 필수 설정이 없거나 연결 확인이 무효면 UI가 필요한 설정을 안내한다. 같은 cfg를 CAN과 Diag에 동시에 사용하지 않는다.
2. 실제 시작 때 측정·블록·외부 기록 여부·최종 이름 충돌을 재검사한다. 사용자가 F9를 켰으면 같은 cfg·블록의 측정 대기는 연결 확인 없이 재검사할 수 있다.
3. 선택한 고유 작업 폴더를 만들고 CANoe 출력 경로·분할 옵션 적용을 확인한다. 실패하면 기존 기록·최종 파일은 유지한다.
4. 세션 ID·역할별 경로·예약 번호·다음 번호를 SQLite에 저장한 다음 외부 기록을 시작한다. 예약 전 차단은 미소비, 예약 후 실패는 번호 유지다.
5. Zipy가 있으면 그 기록을 먼저 요청하고 CANoe 역할 그룹을 시작한다. 모든 선택 대상이 확인돼야 기록 중이 된다. 정확한 동시 취득이나 시계 동기화를 보장하지 않는다.

기존 수동 기록은 앱이 대신 정지하지 않는다. 수동 기록만 멈춘 같은 cfg·유일 블록의 파일명 변경은 허용하되, 이번 출력 적용 이후의 외부 변경·블록 구조 변경은 차단한다.

## 기록 중 감시와 이상 정지

선택한 역할의 도구 상태를 확인한다. CAN·Diag는 측정·선택 trigger·응답 상태를 확인하며 실제 CAN 신호/프레임 미수신은 감시하지 않는다. Zipy는 NIC 링크와 지정 수신 흐름을 확인한다.

기본 Zipy 규칙은 Source MAC 접두사 `02:00:00`, 시작 유예 2000ms, 미수신 2000ms, 2초 평균 최소 100pps다. 지속 저수신도 규칙 기준으로 판단한다. 저장된 사용자 규칙이 우선한다. 규칙은 원본 캡처 필터가 아니며 다른 Source도 저장한다. 규칙 삭제·0pps 설정의 의미는 [사용자 가이드](../../user_guide/README.md)를 따른다.

| 확인한 상황 | 현재 처리 |
| --- | --- |
| CANoe 측정 또는 선택 블록 중지, 도구 오류·응답/상태 확인 실패 | 대상·원인 표시 후 전체 선택 기록 정지 |
| 선택 NIC 단절 또는 Zipy 규칙 위반 | 전체 선택 기록 정상 정지·파일별 보관 시도 |
| Zipy 감시 관측 확인 불가 | 확인 불가로 표시, 정상 유예/샘플 대기와 구분하고 5초 지속 시 정지 |
| 수신 위반 뒤 곧바로 수신 복구 | 확인한 위반을 유지해 같은 구간 정지를 놓치지 않음 |
| 표시 요약 누락·드라이버 원본 drop | 서로 다른 통계로 남김. 하나로 다른 하나의 누락을 단정하지 않음 |
| CAN 통신선만 무수신이고 측정·기록 도구는 유지 | 자동 수신 감지 미지원. Trace·원본으로 별도 확인 |

실패 팝업은 파일 정리·X를 기다리게 하지 않는 비모달 알림이다. 동일 구간의 같은 실패는 반복 표시하지 않으며 동시 대상 오류는 함께 안내한다. 실패 구간을 전체 성공으로 바꾸거나 같은 세션의 실패 대상을 자동 재시작하지 않는다.

## 메인 정지와 파일 완결

메인 정지는 선택 구간 기록에 정상 정지를 요청하며 CANoe 측정·다른 기록 블록을 유지한다. BLF는 trigger 정지·출력 복구·완결 확인을 수행하고 필요하면 고유 내부 출력 전환으로 마지막 버퍼/헤더를 완성한다. 내부 전환은 추가 사용자 번호를 소비하지 않는다.

CANoe의 핸들 보유 자체와 파일 불완전을 구분한다. 정지한 완전 BLF의 변경 없는 안정된 복사본을 검증해 보관할 수 있다. 실제 종료·완결을 확인하지 못한 파일을 성공으로 승격하지 않는다. 보관된 대상은 유지하고 실패 대상은 실제 경로·검사 결과로 남긴다.

정지한 동일 소유 블록의 기존 출력 이름 복구만 거부됐으면 snapshot을 보존하고 다음 구간을 허용할 수 있다. 이는 보관 실패를 무시한다는 뜻이 아니며 임시 출력 경로를 원본 cfg에 저장하지 않는다.

## 현재 작업 제한

아래는 현재 Runtime 요청별 제한이며 전체 버튼 소요시간 보장이 아니다. worker 내부 검사·파일 처리·그룹 순서가 추가될 수 있다. UI에서 모두 임의 조절하는 설정으로 설명하지 않는다.

| 요청 | 현재 제한 |
| --- | ---: |
| CANoe 연결 또는 시작 전 prepare | 45초 |
| CANoe 출력 configure·restore | 15초 |
| 역할 그룹 start | 18초 |
| 기록 상태 조회 | CAN/Diag 포함 1.5초, Ethernet만 0.6초 |
| 정상 stop | 35초 |
| 보관 inspect | CAN/Diag 120초, Ethernet 65초 |
| X guard | 약 1초 후 강제 종료 요청, 반복 X는 즉시 요청 |

시간 초과는 실제 정지의 증거가 아니다. 명령·세션 ID가 다른 늦은 응답을 현재 성공으로 쓰지 않고 실제 상태를 확인한다. UI 스레드는 COM·worker 응답·디스크 정리를 직접 기다리지 않는다.

## X와 재실행

X는 정상 보관의 대체가 아니다. 이번 실행의 worker·dumpcap job·검증된 전용 CANoe 핸들에 종료를 요청하고 미완료 소유 작업 구간을 폐기한다. 전용 CANoe 종료 신호는 coordinator가 바빠도 별도로 요청하며 종료 완료를 기다리지 않는다. 프로세스명 일괄 종료를 하지 않는다. cfg는 자동 저장하지 않는다.

재실행은 알려진 소유 작업 경로와 미완료 DB 이력을 failed/discarded로 정리한다. 작업 폴더가 이미 없어도 이력을 정리하며 잠긴 소유 파일은 재시도하되 새 기록을 막지 않는다. 완료·외부 파일·예약 번호는 유지한다. 비정상 종료에서 진단의 끝부분·외부 도구 정지가 보장되는 것은 아니다.

## 파일 작업과 이력

보관 완료 후 직전 세션을 이름 변경·삭제할 수 있다. 변경 의도와 파일별 실제 결과를 저장하고 충돌·잠금·외부 변경에서는 강제 해제하지 않는다. 이름 변경은 입력 제목을 사용하며 확장자와 Diag 구분을 유지한다. 다음 번호는 변경하지 않는다.

설정·번호·이력은 사용자 프로필 DB, 캡처는 지정 폴더, 진단은 EXE별 폴더, 내보낸 ZIP은 바탕화면에 분리한다. 상세 순환·DB 아카이브와 제출 절차는 [진단 보관](../guides/diagnostics.md)을 따른다.
