# 5단계 — CAN/Diag 구간 BLF 기록 연동 (0.5.0 시험용)

2026-10-18 · 구현과 장비 없는 검증을 완료하고 대표 .cfg 현장 시험을 대기한다. 사용자가 .cfg를 준비 중이므로 실제 CANoe 창·측정·차량 장비는 이번 구현 과정에서 열거나 제어하지 않았다.

## 구현

- CAN/Diag 각각 별도 프로세스의 COM STA에서 `DispatchEx("CANoe.Application")`로 전용 참조를 생성한다. 기존 구성이 반환되면 덮어 열지 않고 거부한다. 활성 객체 테이블을 통한 임의 창 연결, 프로세스명 일괄 종료, CANoe Quit 호출을 사용하지 않는다.
- 사용자가 지정한 .cfg를 자동 저장 없이 열고, 로드된 전체 경로를 확인한다. 기존 LoggingCollection만 사용하며 블록을 추가하지 않는다. 블록이 하나면 선택을 기억하고 여러 개면 설정에서 명시적으로 선택한다. .cfg 변경 시 이전 블록 선택을 초기화한다.
- 사용자가 전용 CANoe 창에서 측정을 시작한다. AutoLog는 측정 Start/Stop을 호출하지 않는다. 구간 직전에 구성·블록 COM identity·측정 실행·Trigger.Active·출력 경로·파일 분할 설정을 확인한다. 동일 .cfg를 CAN/Diag에 동시에 쓰는 조합은 거부한다.
- 고유 임시 BLF 경로를 블록에 적용·재조회한 다음 공통 번호를 예약한다. Ethernet 선택 시 먼저 시작하고 CAN/Diag에 구간 시작 명령을 보낸다. Trigger 활성과 정확한 경로의 BLF 헤더를 확인해야 기록 중으로 표시한다.
- 정상 정지는 선택 대상의 Trigger.Stop만 호출한다. 모든 대상에 정지를 먼저 보낸 뒤 응답을 기다린다. 트리거 종료와 Windows 배타 파일 열기로 닫힘을 확인한 뒤 BLF 구조를 읽고 교체 없이 최종 경로로 보관한다. 원래 .cfg의 자동 Save/SaveAs, CAPL·시스템 변수 추가를 하지 않는다.
- 부분 시작 실패는 발행한 모든 시작 대상의 정지를 확인하고 번호를 재사용하지 않는다. 기록 중 한 대상 실패는 다른 대상의 기록을 유지한다. 정지 미확인은 해당 작업 파일을 보존하고 완료로 표시하지 않는다. 다른 대상의 닫힌 파일은 별도로 검사·보관한다.
- CANoe는 Ethernet의 kill-on-close Job에 넣지 않는다. 비정상 종료에도 강제 정리 대상은 앱의 worker이며 실제 CANoe를 강제 종료해 정상 종료로 처리하지 않는다. 정상 앱 종료 시도 측정·창을 닫는 API를 호출하지 않는다. COM 참조 해제 후 창 유지 여부는 현장 시험에서 확인한다.
- worker에서 연결·경로 적용·Trigger Start/Stop 직전에 진단을 부모에게 전송한다. 응답이 멈춰도 마지막 호출 지점·명령/세션 ID가 상시 개발자로그와 버그리포트에 남는다. 프레임 payload는 기록하지 않는다.

## BLF 검사 범위

`storage/blf.py`는 제한된 메모리로 전체 컨테이너를 순차 읽는다. LOGG/LOBJ 헤더·선언 파일 크기·압축 스트림 끝과 무결성·확장 길이·객체 경계·미완성 객체를 검사한다. 미지원 압축/헤더 버전은 보관 성공으로 승격하지 않는다. 객체 내용의 차량 신호 의미·채널/출처 적합성·기대 통신 수신이나 무손실 취득은 이 검사로 판정하지 않는다.

Vector 샘플에서 헤더 객체 수가 복구 지점 등 메타데이터를 포함한 실제 물리 객체 수보다 작을 수 있음을 확인했다. 두 수를 별도로 저장하며 헤더보다 적게 읽힌 경우는 거부한다. 헤더 수와 물리 객체 수가 항상 같다고 가정하지 않는다.

## 시험 PC에서 확인할 순서

1. 기존 작업을 정리하고 0.5.0 배포 폴더의 AutoLog.exe를 실행한다. CAN만 먼저 선택하고 저장 폴더·prefix를 지정한다. 장비/라이선스는 CANoe에서 정상 사용 가능한 상태로 준비한다.
2. 설정 → CAN·Diag 구성에서 CAN의 대표 .cfg를 선택하고 **연결 확인**을 누른다. AutoLog가 연 전용 CANoe 창을 사용한다. 이미 열려 있는 무관한 창에 자동 연결하지 않는다.
3. Logging Block이 여러 개면 드롭다운에서 원하는 블록을 선택하고 다시 확인한다. 다른 블록을 함께 조작하지 않는다. 이번 초기 연동은 한 블록당 단일 BLF이므로 자동 분할·트리거 후 번호 증가 옵션이 켜져 있으면 CANoe에서 해제해야 한다. 해당 옵션을 AutoLog가 임의로 바꾸지는 않는다.
4. 그 CANoe 창에서 사용자가 측정을 시작한다. 대상 블록이 이미 기록 중이면 CANoe에서 해당 블록의 기존 기록을 종료한다. **연결 확인**이 측정 실행·유휴 기록 블록을 확인하도록 한다.
5. 메인 logging으로 약 3초 기록 → 정지를 3회 반복한다. 매회 서로 다른 번호의 BLF와 보관 결과, CANoe 측정이 계속 실행되는지 확인한다. 최종 BLF는 CANoe/Vector 도구로도 열어 기대 채널·데이터·시간 구간을 확인한다. 사용자가 직접 저장하지 않은 원본 .cfg의 해시/수정시각도 전후 비교한다.
6. 다른 .cfg의 Diag를 같은 방법으로 확인한 후 CAN+Diag, CAN+Zipy, 세 대상 선택 조합을 시험한다. 서로 다른 CANoe의 참조·블록·파일을 독립 제어하는지와 수동 창 종료·구성 교체·측정 중단 때의 부분 실패도 확인한다.
7. 문제가 생기면 **버그리포트**로 바탕화면 ZIP을 만들고 발생 시각, 선택 대상, 단계와 함께 Taegon.Kim에게 전달한다. 닫힘 미확인·검사 실패 파일은 표시된 작업 경로에 보존한다.

최초 연결의 COM 호출·CANoe 자체 확인창이 오래 걸리면 앱은 미확인/시간 초과를 표시한다. 시간 초과를 실제 정지로 간주하거나 자동으로 다른 창에 재접속하지 않는다. CANoe 확인창을 처리한 뒤 상태를 확인한다.

## 검증과 남은 게이트

- 정적 검사 통과, 기본 자동 검사 **250개 통과**. 한국어 CAN·Diag 설정 화면의 렌더링과 블록 드롭다운 배치를 확인했다.
- 장비 없는 자동 검사: COM 대역의 3회 구간 기록, 측정·원본 보존, 기존 구성 교체 거부, 복수 블록 명시 선택, 외부 구성/블록/파일명/측정/분할 변경 차단, 다른 세션 정지 차단, 기록하지 않은 외부 블록 정지 금지, 블록 선택 저장·초기화.
- 공통 제어 장애 주입: 세 대상의 시작 순서, 경로 적용 후 번호 예약, 적용 실패 시 예약 금지, 시작 부분 실패 정리, 한 대상 정지 미확인 시 파일별 보관/보존, 동일 구성 중복 거부와 중간 worker 진단 처리.
- BLF 구조 검사: 압축/비압축·컨테이너 사이에 걸친 헤더/객체·대용량 객체·알 수 없는 객체 유형·빈 파일·잘린/손상/미완결 파일. 설치된 CANoe 19.3.118의 CAN BLF 샘플 6개(최대 4,367,660바이트·431,765객체)를 읽었다. 샘플 payload를 로그나 저장소에 복사하지 않았다.
- 설치된 `Exec32/COMdev/CANoe.tlb`를 읽기 전용으로 확인해 Application.Open, Configuration.OnlineSetup.LoggingCollection, Logging.FullName/FileNameOptions, Trigger.Start/Stop/Active와 Measurement.Running의 존재·호출 형태를 확인했다. CANoe 서버는 활성화하지 않았다. COM IUnknown 비교는 별도 기본 COM 객체로 확인했다.
- **미실행:** 대표 .cfg의 실제 COM 인스턴스 독립성, 측정 유지 중 출력 적용과 3회 BLF 완결, 후행 기록, 원본 해시 보존, 두 CANoe+차량 NIC 복합 시험. 이 게이트 통과 전 CAN/Diag 현장 지원 완료로 표시하지 않는다. 통신 감시 판정과 수동 복구 화면, 고부하/장시간/새 PC 검증도 후속 작업이다.
