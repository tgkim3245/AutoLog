# 라이선스 PC의 실제 CAN/Diag 기록 검증

2026-10-21 / 0.9.7 재시험: [핸들 보유·중첩 번호 수정](canoe_fixes_0_9_7.md)을 반영했다. CAN 단독·CAN+Zipy·Diag 단독 각 3회에서 정지→자동 보관→즉시 다음 기록을 확인한다. CANoe 핸들이 남아 있어도 `canoe.snapshot_sealed`와 최종 BLF 전체 읽기·프레임 수·다음 번호가 맞으면 정상 보관이다. 실패하면 `canoe.command_failed.observed.file`의 실제/선언 크기와 `canoe.file_finalizing`을 확인한다. 아래 과거의 ‘독점 닫힘’은 새 CAN 보관의 필수 조건이 아니며, 다른 앱에서 열린 파일의 이름 변경·삭제에는 계속 적용한다.

2026-10-19 · **아직 수행하지 않은 현장 시험 절차**. 구성 열기·COM API 존재 확인·대역 검사만으로 아래 결과를 통과 처리하지 않는다.

## 준비

1. CANoe 빌드·라이선스 활성/측정 가능 여부, VN 모델·드라이버·CAN/Diag의 실제 채널을 기록한다. View Only 상태에서는 기록 시험을 진행할 수 없다.
2. 대표 CAN/Diag cfg와 필요한 데이터베이스/CAPL 등 의존 파일을 준비한다. 원본은 별도 보관하고 시험 전후 해시를 비교한다. 기존 CAPL 자동시험·송신·로깅 버튼의 실행 상태를 확인한다.

   CAPL 컴파일의 `Error writing binary file ... .cbf: 액세스가 거부되었습니다`는 먼저 [CBF 쓰기 거부 진단](canoe_capl_compile_troubleshooting.md)을 따른다. 2026-10-20 Diag 현장 오류에서는 Defender CFA가 Vector 컴파일러를 차단한 이벤트 1123을 확인했다. 원본 CAPL 수정이나 AutoLog 재빌드로 해결할 오류가 아니다.
3. AutoLog에서 빈 시험 출력 폴더, 구분 가능한 prefix/시작 번호를 지정한다. 기본 선택 CAN·Zipy 중 시험할 대상만 체크한다.
4. CAN·Diag 카드에서 서로 다른 cfg를 지정하고 연결 확인한다. **서로 다른 CANoe PID와 정확한 cfg**가 표시되는지 확인한다. CAN의 `CAN_Logging` BLF, Diag의 `Logging` BLF를 선택한다. CAN의 `ETH_Logging` PCAPNG는 CAN BLF 대상이 아니다.
5. 독립 연결 설정이 처음 필요한 경우 기존 CANoe 작업을 저장하고 창을 닫은 후 다시 연결한다. AutoLog가 원본 can.ini를 백업하고 필요한 모드를 준비한다. 공유 창을 대신 제어하지 않는다.
6. 각 전용 CANoe 창에서 논리 CAN→실제 장치/포트 매핑과 **cfg에 필요한 모든 버스 옵션 라이선스**를 확인한다. CAN 라이선스가 있어도 cfg가 Ethernet을 요구하면 해당 옵션 없이는 측정이 중단될 수 있다. 실제 0.9.0 현장 시도에서 `CAN (available) / Ethernet (missing)`이 보고됐다. BLF 블록 선택이나 Zipy 해제는 cfg의 요구 옵션을 제거하지 않는다. 적합한 라이선스/활성 상태 또는 시험 담당자가 별도로 준비한 CAN 전용 cfg가 필요하며 원본 cfg를 AutoLog가 편집하지 않는다.
7. 시험 환경의 절차에 따라 사용자가 각 전용 CANoe 창에서 **F9로 측정 시작 → Trace의 실제 CAN 수신 확인 → AutoLog 연결 확인**을 수행한다. 측정 실패 시 먼저 CANoe Write 창 오류를 해결한다. 다른 로깅 버튼을 누르지 않고 선택 블록의 기록은 정지 상태로 둔다.
8. 먼저 수동 기록을 시험했다면 그 기록만 수동 정지하고 F9 측정은 유지한다. 0.9.3에서는 같은 cfg·이름이 유일한 BLF 블록의 파일명 변경/자동 번호 증가만 있으면 연결 재확인 없이 logging을 누를 수 있다. 정지 후 시작 직전의 최신 수동 파일명·옵션으로 복구되고 수동 파일은 유지되는지 확인한다. 블록 이름/순서/개수·다른 블록 출력·cfg 변경은 재연결이 필요하다.

0.9.0 이상은 연결 카드의 로컬 채널 번호·장치 시리얼·물리 포트를 Vector Hardware Manager와 대조한 뒤 **채널 기준 저장**을 시험한다. 재연결 시 일치, 다른 장치/포트 매핑 시 불일치와 시작 차단, 장치 조회 실패 시 확인 불가를 확인한다. 원격/분산·가상 장치는 로컬 XL 결과로 통과 처리하지 않는다. 결과는 [버전별 환경 검증표](canoe_support_matrix.md)에 추가한다.

## 기본 구간 기록

| 시험 | 반복 | 확인할 결과 |
| --- | --- | --- |
| CAN 단독 | 3회 | 매회 새 BLF, 번호 한 번 증가, 기대 CAN/CAN FD 채널·ID/시간 구간 확인 |
| Diag 단독 | 3회 | 매회 `_Diag_` 이름의 새 BLF, 기대 진단 통신 확인 |
| CAN+Diag | 3회 | 같은 번호의 BLF 2개, 서로 다른 cfg/PID, 한쪽 제어가 다른 블록에 영향 없음 |
| CAN+Zipy, Diag+Zipy, CAN+Diag+Zipy | 각 1회 이상 | 같은 번호의 선택 파일만 생성, 보관 경로·확장자 일치, 시작 시간차를 기록 |
| Zipy 단독 | 1회 이상 | 차량 NIC로 pcap/pcapng 기록 확인. localhost 결과와 구분 |

각 회차는 `logging` 시작 → 시험 통신 확인 → `logging` 정지 순서로 수행한다. 처음에는 10초 정도의 짧은 구간으로 파일 생성/닫힘부터 확인하고, 성공 후 조건별 장시간 시험으로 확장한다.

정지 후 CANoe **측정이 계속 실행**되는지, 선택 블록의 출력 경로와 자동 증가/분할 옵션이 이전 값으로 복구됐는지 확인한다. 보관된 BLF를 CANoe/검증된 뷰어로 실제 열어 필요한 프레임과 시간 범위를 확인한다. AutoLog의 구조 검사만으로 내용 검증을 대신하지 않는다. 0프레임 파일은 보관 성공일 수 있지만 기대 통신 시험의 성공은 아니다.

0.9.4 재시험에서는 CAN+Zipy를 3회 반복하고 매회 정지 버튼→파일 보관까지의 시간을 기록한다. 0.9.3 현장에서는 시작 후 CAN trigger가 정지해도 파일이 잠겨 28초 뒤 미완료가 됐다. 새 순서인 trigger 정지→출력 경로 복구→파일 닫힘이 실제 CANoe에서도 완료되는지 확인한다. 다음 기록이 막히면 강제 삭제 대신 정지 재시도와 버그리포트를 사용한다.

## 이상 조건 — 준비된 시험 환경에서만 수행

- 설정의 기록 블록 변경/삭제/순서 변경 후 연결 확인 없이 logging: 시작 차단, 새 번호 예약과 다른 블록 제어 없음. 다시 연결 확인하면 의도한 블록으로 재선택 가능.
- 0.9.2: 매 조회마다 COM 객체 주소가 달라져도 cfg·선택 인덱스·블록 목록/순서/이름과 단계별 출력 경로가 일치하고 선택이 유일하면 재조회한다. 시작·조회·정지는 이번 세션의 정확한 임시 출력 경로, 시작/조회는 자동 분할 꺼짐도 확인한다. 실제 논리 선택·외부 출력 변경은 계속 차단한다. 영구 블록 ID가 없어 동일 메타데이터로 삭제·재생성한 블록은 객체 주소로 구별하지 못한다. 자세한 기준은 [수정 기록](canoe_fixes_0_9_2.md)을 따른다.
- 미리 기록 중인 선택 블록: 시작 차단, 기존 기록 유지.
- 0.9.3: 대기 중 선택 BLF 파일명 변경은 수동 trigger 정지·유일한 이름·같은 cfg/순서/개수/이름·다른 블록 출력 유지 조건에서만 허용한다. prepare와 configure 사이 번호 증가도 최신 복구 경로로 반영한다. PCAPNG 전환·중복 이름·다른 블록 출력 변경은 차단한다. configure 이후 외부 출력 경로 변경은 이전과 같이 차단한다.
- 한 대상 시작 실패: 이번 시도에서 시작한 나머지 구간만 정리, 예약한 번호 유지, 부분 파일 보존.
- 기록 중 한 CANoe 측정/창이 외부에서 정지됨: 다른 기록 유지, 실패 대상·시각 표시. 차량과 장비에 영향을 주는 조작은 시험 담당자가 통제한다.
- 한쪽 정지 응답 지연: 다른 쪽은 정지·보관, 미확인 쪽은 미완료. 재시도 후 먼저 보관한 파일의 경로·검사 결과·내용 유지.
- CANoe 외부 파일명/옵션 수정 충돌: 임의 덮어쓰기/다른 기록 정지 없음. 복구 실패를 안내하고 원래 설정의 스냅샷 보존.
- 파일명 충돌·저장 권한/용량 부족·파일 열림: 기존 파일 유지, 실패 경로 확인. 소유권이 불명확한 임시 파일 자동 삭제 없음.
- 메인 X: 활성 구간 정상 정리 후 AutoLog 종료. CANoe 측정/창 유지. 미확인 기록/출력 복구는 종료 보류.

## 결과와 전달 자료

회차마다 AutoLog 버전, 도구/드라이버 버전, 선택 조합·cfg 별칭·PID·블록, 측정 유지 여부, 원래/복구 출력 옵션, 파일명·크기·구조 검사와 실제 프레임 확인 결과, 시작/정지 시각·오류를 기록한다. 업무 원본과 상세 경로는 로컬에 두고 Git에는 익명화한 요약만 남긴다.

문제가 생기면 강제로 정리하기 전에 **버그리포트**를 눌러 바탕화면 ZIP과 발생 시각·조작 순서를 Taegon.Kim에게 전달한다. 자동 이메일 전송은 없다. 실제 BLF/PCAP 추가 전달이 필요한 경우 개발자로그 ZIP과 별도 자료로 취급한다.
