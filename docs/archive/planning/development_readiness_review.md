검토일: 2026-10-17 (Asia/Seoul)
범위: 최신 요구사항·설계·개발 환경·외부 연동·검증·팀 배포·운영/복구·설치 의존성.
결과물: [설치 목록](installation_matrix.md), [단계별 개발·배포 계획](development_delivery_plan.md), [제어 정책](../../reference/control_policy.md).
이번 작업은 검토·설계 문서 보완이다. 프로그램 구현·설치·실제 로그 취득·패키징 실증을 수행하지 않았다.

## 1. 결론과 착수 범위

Python + PySide6의 로컬 Windows 앱으로 구현하는 방향은 유지한다. 환경 정보와 예외 동작이 정리돼 개발 환경 준비·이름/번호/상태·가상 연동 개발은 시작할 수 있다.

**실제 외부 제어와 팀 배포까지 검증됐다는 의미는 아니다.** 본 연동의 구조를 확정하기 전에 CANoe 독립 제어, 측정 유지 중 구간 파일 완결, TShark 기록/요약/정상 정지와 패키징을 우선 실증한다.

기존 .cfg에 CAPL·시스템 변수를 추가하지 않는 경로를 우선한다. 필요한 관측을 얻을 수 없으면 해당 감시 지원을 미검증/미지원으로 명시하고, 프로젝트 복사본에서의 보조 기능을 별도 검토한다. 원본 .cfg를 자동 수정·저장하지 않는다. 실행 중 출력 경로를 적용하는 작업은 원본 파일 저장과 구분한다.

## 2. 사용자 답변으로 확인한 환경

| 항목 | 현재 기준 |
| --- | --- |
| 실제 시험 PC | Windows 11 64비트 |
| 설치 권한 | 사용자 요청에 따라 별도 차단 조건으로 취급하지 않음 |
| 보안 예외 | 사용자 예상상 별도 예외 등록 불필요. 예외 해제·정책 변경을 프로그램이 수행하지 않음 |
| 인터넷 | 설치 준비 때 사용 가능. 앱 실행·캡처·저장은 인터넷 의존 없이 동작 |
| CANoe 라이선스 | VN CAN 장비 직접 연결을 통한 인증이라는 사용자 설명 |
| 사용 규모 | 팀 여러 PC, 정확한 수량은 미정. 현재 기능 개발의 차단 조건 아님 |
| 저장 | 각 PC의 로컬 디스크 |
| 일반 구간 | 약 1분 |
| 긴 구간 | 30분을 넘길 수 있음. 최대 시간은 미확정 |
| 파일 크기 | Wireshark 로그가 1GB를 넘을 수 있음. 최대 트래픽/파일 크기는 미확정 |
| 원본 구성 변경 | 기존 .cfg를 되도록 유지. CAPL/시스템 변수 추가 허용 여부는 확인 필요 |

PC 수를 질문한 이유는 드라이버 이용/재배포 조건과 배포 확인 범위를 정하기 위해서였다. 사내 서버나 PC 수 제한을 앱에 도입하려는 요구는 아니다. 사용자는 앱 온라인 계정·활성화 서버·자동 외부 전송을 요구하지 않았다.

## 3. 최신 요구사항의 해석

| 항목 | 현재 구현 기준 |
| --- | --- |
| 화면 이름 | CAN=CANoe 슬롯 1, Diag=CANoe 슬롯 2, Zipy=Wireshark 계열 Ethernet 캡처 |
| 메인 화면 | 약 480px 폭의 컴팩트한 카드 3개, 공통 logging, 이력, 고정 이름 변경 입력/버튼 |
| 설정 | RBS/.cfg·Zipy 연결·NIC·형식·prefix·다음 번호·로컬 저장 폴더 |
| 이름 | CAN: VIL_7.blf, Diag: VIL_Diag_7.blf, Ethernet: VIL_7.pcap/pcapng |
| 이름 변경 | 직전 세션의 prefix만 변경. Diag 구분자·기록 때 사용한 인덱스·확장자 유지 |
| 번호 | 설정 적용 시 충돌 검사, 시작 직전 재검사, 실제 기록 전 영구 예약 |
| 제어 | 통합 프로그램이 연 .cfg만 제어. 사용자가 켠 무관한 창 연결 제외 |
| 측정 | 사용자가 CANoe 측정을 시작·유지하고 패널은 구간 기록만 제어 |
| 실패 | 시작 단계 실패는 이번 시작 정리. 기록 도중 실패는 다른 대상 유지 |
| 관찰/감시 | 최근 패킷 목록. 선택 대상의 실제 기록 구간에만 통신 감시 |
| 보관 | 고유 임시 폴더 → 닫힘/읽기 확인 → 교체 없는 최종 보관 |

문자열을 파일명에서 다시 추측하지 않는다. 세션 자료에 역할·prefix·인덱스·형식과 실제 경로를 저장하고 같은 이름 생성 함수를 미리보기·검사·기록·이름 변경에 사용한다.

새 요구사항 검토에서 이전 제어 정책의 CAN1/CAN2 파일 예시와 README의 검증 건수가 과거 상태인 것을 확인했다. 현행 명명과 검증 계획에 맞춰 정리했다.

## 4. 구현 전 확인할 외부 연동

| 우선순위 | 검토 항목 | 완료 기준 / 실패 시 처리 |
| --- | --- | --- |
| 먼저 실증 | 두 CANoe에 독립된 제어 참조 | A만/B만/양쪽 제어, 한쪽 종료·재시작에서 다른 대상에 영향 없음. 단순 프로세스 두 개나 .cfg 경로 두 개로 보장하지 않음 |
| 먼저 실증 | 기존 Logging Block 외부 제어 | 원래 버튼의 구간 저장을 동일 측정에서 3회 재현. 파일명 적용·후행 기록·닫힘·별도 파일을 확인 |
| 먼저 실증 | 원본 .cfg 보존 | 파일 해시/수정 시각 비교로 자동 저장 없음을 확인. 실행 중 경로 적용이 만드는 미저장 상태는 구분 |
| 먼저 실증 | TShark 기록+필드 출력 | 한 NIC의 pcap/pcapng·IP/비IP·0패킷·다음 구간·정상 정지 확인 |
| 먼저 실증 | 패키징한 앱의 외부 실행 | 소스 실행과 실제 EXE 둘 다 CANoe/TShark 실행·Qt 플러그인·COM·정지 확인 |
| 기능별 확인 | CAN 수신 시각·장비/채널 정보 | 실제 읽을 수 있는 정보와 미지원 정보를 구분. 값 고정으로 미수신을 판정하지 않음 |
| 기능별 확인 | BLF 검사 범위 | 기존 CANoe/검증된 판독 수단으로 샘플의 구간·내용 확인. 단순 크기/헤더 검사만으로 전체 의미 검증 완료를 주장하지 않음 |

CAPL이 유리한 이유는 CANoe 안에서 수신 이벤트/타이머와 기존 프로젝트 정보를 관측할 수 있기 때문이다. 기본 구간 로깅을 외부에서 시작·정지하는 데 CAPL이 필수라는 근거는 없다. 프로젝트 수정 없는 COM·기존 관측값을 먼저 확인한다.

실증이 실패하면 공식 지원 경로와 실제 설정을 조사한다. 화면 좌표 클릭·강제 종료·다른 인스턴스 자동 연결·원본 CAPL 추가로 몰래 대체하지 않는다.

## 5. 코드 구조와 프로세스 설계

| 모듈 | 책임 |
| --- | --- |
| ui | Qt Widgets·표시 언어·메인/설정/패킷 창. 캡처 API 직접 호출 제외 |
| core | 불변 세션 계획·대상별 명령·취소·기록 상태·타임아웃·종료·부분 실패 |
| adapters | CANoe 슬롯별 COM, Ethernet 도구 실행·출력·정상 종료 |
| monitors | 원본/화면과 분리된 관측·규칙·유효성·미설정·복구 |
| storage | SQLite·번호 예약·세션/파일 자료·명명·교체 없는 보관·파일 작업 이력 |
| diagnostics | 도구 버전·설정/지원 조합·로컬 진단 정보. 외부 자동 전송 없음 |

CANoe COM 객체는 생성한 실행 문맥 안에서 사용하고 다른 프로세스에 객체 자체를 전달하지 않는다. UI와 각 대상 실행부는 명령/응답 자료만 교환한다. 한쪽 정체가 나머지 정지를 막지 않아야 한다.

명령은 session_id·command_id·target_generation으로 식별한다. Start/Stop을 명시하고 재요청으로 토글하지 않는다. 알 수 없는 상태를 자동 재시작/자동 정상으로 복원하지 않는다.

Windows 패키징 시 작업 프로세스가 GUI를 재실행하거나 단일 실행 잠금에 막히지 않게 진입점을 분리한다. multiprocessing을 채택하면 main guard와 freeze_support를 초기화 전에 처리한다. [PyInstaller 작업 프로세스 안내](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html)

Frozen 앱은 DLL 검색 환경을 변경할 수 있어 외부 TShark 실행에 영향을 줄 수 있다. 전용 실행부에서 외부 실행 환경을 정리하고 실제 배포물로 검증한다. 시스템 PATH·레지스트리를 영구 변경하는 해결책을 기본으로 두지 않는다. [외부 프로그램 실행 주의점](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html)

## 6. 데이터·설정 계약

| 자료 | 핵심 필드 |
| --- | --- |
| TargetBinding | 역할, .cfg 전체 경로, 기록 블록, 확인된 제어 참조 대응, 세대, 마지막 확인 시각 |
| CapturePlan | 세션 ID, 설정 버전, 선택 대상, prefix, 인덱스, 형식, 임시/최종 경로 |
| TargetState | 연결·측정·기록·관측·오류 근거·마지막 응답 |
| CaptureFile | 역할, 생성/닫힘/보관 결과, 실제 경로, 크기, 검사 범위, 이름 변경/삭제 이력 |
| Observation | 수신 시각, 로컬 수신/지속 시간 기준, 관측 유효성·지연·누락 근거 |
| Event | 코드, 시각, 대상, 등급, 파라미터, 원문 |
| ReleaseInfo | 앱 버전, 소스 변경 식별자, Python/의존성 버전, 지원 외부 도구 조합 |

기본 기술은 Python dataclass/enum + 표준 JSON·SQLite다. 설정은 버전 필드를 두고 알려지지 않은 형식은 조용히 적용하지 않는다. PC별 실경로·NIC·장비·원본 구성은 각 PC에서 입력하며 다른 PC의 식별자를 자동 재사용하지 않는다.

설정 적용은 입력 전체를 한 번에 검증하고 저장한다. 충돌한 prefix/인덱스는 적용하지 않는다. 검사 중 설정·선택 대상이 바뀌면 이전 비동기 검사 결과로 새 설정을 확정하지 않는다. 실제 시작 전에는 현재 설정으로 다시 확인한다.

번호는 PC/Windows 사용자별 로컬 상태다. 여러 PC가 공유하는 중앙 번호 서버는 현재 범위에 없다. 이름 변경·삭제·앱 버전 교체로 번호를 자동 되돌리지 않는다.

## 7. 오프라인 실행

앱은 외부 웹 API·로그인·텔레메트리·자동 업데이트·실행 중 패키지 다운로드를 사용하지 않는다. 도구는 로컬 절대 경로로 실행하고 앱 프로세스 간 통신은 로컬 IPC로 한다.

TShark는 주소/포트 이름 해석을 끄는 -n 등 고정 옵션을 사용해 표시 과정에서 DNS 조회가 발생하지 않게 한다. 호스트 이름을 포함한 캡처 필터·외부 플러그인 등도 오프라인 검증 대상이다. [TShark 옵션](https://www.wireshark.org/docs/man-pages/tshark.html)

차량 Ethernet 연결과 인터넷 연결은 별개의 조건이다. 수집에는 선택한 차량용 NIC가 필요하다. 사용자 설명의 VN 장비 인증을 실제 시험 PC에서 확인하며 기존 라이선스·드라이버를 앱이 재설정하지 않는다.

## 8. 성능·용량·장시간 취득

- 대표 구간 60초, 장시간 기준 30분 초과, 초기 soak 목표 60분을 시험 계획으로 둔다. 60분은 검증 목표이며 이미 보장한 최대 사용 시간이 아니다.
- 실제 저장 파일이 1GiB를 넘는 조건을 시험한다. 전체 파일·전체 패킷 목록을 메모리에 읽지 않는다.
- 원본 파일은 외부 취득 도구가 기록하고, 화면은 최근 1,000건, 이벤트는 최근 200건을 제한해서 보관한다. 이력/관측 큐가 무한 증가하지 않게 한다.
- 화면 반영 약 250ms는 초기 설정이다. 실제 패킷량에 대해 CPU·메모리·해석 지연·드롭·파일 쓰기 속도를 함께 측정한다.
- 화면 항목 교체는 원본 삭제가 아니다. 해석 지연·관측 누락이 있으면 통신 정상/미수신을 확정하지 않는다.
- 파일 크기는 구간 길이만으로 결정하지 않는다. 실측 기록 속도와 장시간 결과로 필요한 여유 공간·지원 범위를 정한다. 회전 덮어쓰기·자동 파일 분할은 현재 요구에 추가하지 않는다.
- 최초 지원 저장은 로컬 NTFS를 우선 검증한다. 실제 로컬 파일 시스템이 다르면 대용량 파일/이동 동작을 확인한 뒤 지원을 선언한다. 네트워크/클라우드 폴더를 기본 경로로 잡지 않는다.
- 디스크 공간·쓰기 오류가 실행 중에도 발생할 수 있다. 파일별 오류를 표시하고 쓰기 실패 대상을 정상 로깅으로 유지하지 않는다.

1GB 로그가 1분 만에 생긴다는 정보는 확인되지 않았다. 사용자 답변의 구간 길이와 용량을 조합해 예상 트래픽을 임의 산출하지 않는다.

## 9. 오류·복구·파일 완결

이미 확정한 시작 단계 실패 정리와 기록 도중 다른 대상 유지 정책을 적용한다. 상태 미확인 대상이 남으면 새 세션/파일 관리를 막고 원인을 표시한다.

실제 파일은 지정 폴더의 .vil_work/세션 ID 아래 기록한다. 종료·읽기 확인 후 같은 볼륨의 최종 경로로 교체 없이 보관한다. 여러 파일의 보관/이름 변경을 하나의 원자적 작업이라고 표현하지 않는다.

재실행 복구에서는 저장된 작업 의도와 실제 경로를 대조한다. 이전 CANoe에 자동 접속하지 않으며 사용자에게 잔류 기록을 확인하도록 안내한다. 사용자 확인 입력만으로 파일 닫힘이나 정상 완료를 추정하지 않는다.

로그 원본 자동 삭제·디스크 확보를 위한 과거 로그 삭제·파일 잠금 강제 해제는 하지 않는다. 중요한 이벤트가 디스크에 저장되지 못하면 해당 오류도 표시하며 정상 기록으로 숨기지 않는다.

## 10. 화면·사용 흐름 확인

약 480px는 화면 설계 기준이다. Windows 배율 100/125/150/200%에서 카드·전체 파일명 접근·고정 이름 변경 입력·포커스/키보드·한국어/영어를 검사한다.

패킷 보기의 창 닫기·필터·화면 일시 정지는 취득/감시와 독립이다. 메인 X는 취득을 유지하는 숨김이며 트레이 복구를 제공한다. 명시적 종료는 현재 구간 정리 후 수행하고 CANoe 측정·창은 유지한다.

이벤트는 번역된 완성 문자열만 저장하지 않는다. 앱 설명과 원문 근거를 함께 보존해 언어를 바꿔도 기존 이력이 일관되게 보인다.

## 12. 배포·업데이트·원복

Windows x64에서 PyInstaller 폴더 배포물을 만든다. Python과 앱 의존성은 포함하고 CANoe·Wireshark·Npcap·드라이버는 외부 설치본을 사용한다. 실행 파일 하나만 떼어 배포하지 않는다.

배포 폴더에는 앱 버전·파일 해시 목록·지원 도구 조합·기본 안내·라이선스 자료·릴리스 변경·복구 안내를 포함한다. 설정/번호 DB/실제 로그는 배포 폴더와 분리해 새 버전 복사로 덮어쓰지 않는다.

업데이트는 활성/종료/미확인 세션이 없는 시점에 사용자가 수행한다. DB 스키마 변경 전 백업과 이행 검사를 한다. 새 세션을 기록한 뒤 과거 DB를 통째로 복원해 번호·결과를 잃지 않게 한다. 이전 바이너리로 돌아갈 때도 DB 호환성을 확인하며 불일치 상태에서 강행하지 않는다.

자동 업데이트·사내 서버·온라인 활성화는 도입하지 않는다. 현재 보안 예외는 필요하지 않을 것으로 설명받았으므로 코드 서명 구매/보안 설정 해제를 선행 조건으로 요구하지 않는다. 실제 배포물 실행 여부는 정상 사용자 환경에서 확인한다.

## 13. 배포 이용 조건

Python·Qt/PySide6·pywin32·PyInstaller와 그 실제 포함 의존성의 버전/고지 자료를 배포물에 정리한다. Qt LGPL 조건의 충족 방식은 사용하는 모듈·배포물 기준으로 확인한다. 폴더 배포를 선택했다는 사실만으로 모든 이용 조건이 충족된다고 간주하지 않는다. [Qt 공식 안내](https://www.qt.io/development/open-source-lgpl-obligations)

Npcap은 시스템 수·Wireshark 사용 예외·재배포·무인 설치 조건을 구분한다. 기존 Wireshark/TShark 설치본을 사용하고 드라이버를 앱 설치물에 묶지 않는다. 정확한 대수는 기능 개발을 막지 않으며 배포 방법이 바뀔 때 조건을 다시 검토한다. [Npcap 공식 조건](https://npcap.com/)

프로그램이 원본 로그를 외부로 자동 보내지 않도록 한다. 문제 재현 자료나 발표 자료를 공유할 때는 사용자가 선택한 비식별 샘플·요약·화면을 사용한다.
