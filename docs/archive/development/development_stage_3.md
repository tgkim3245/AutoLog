# 3단계 — 실제 Ethernet 기록

> 과거 기록: 이 문서는 작성 당시의 변경·검증 근거를 보존합니다. 현재 동작과 남은 확인 사항은 [현재 구현 상태](../../reference/implementation_status.md)를 따릅니다.

2026-10-18 · VIL Logging 0.3.0

[실행 파일](../../../outputs/stage3/VILLogging/VILLogging.exe). 기존 앱을 설정의 프로그램 종료로 닫고 새 폴더의 EXE를 실행한다. 창 X는 숨김이다. EXE와 `_internal` 폴더를 함께 유지한다.

## 사용 흐름

1. 설정의 **Ethernet 연결**에서 TShark 경로, 장비가 연결된 네트워크 하나, 저장 형식을 확인한다. 기본 형식은 pcap이다. 파일 검사에 같은 설치 폴더의 capinfos.exe도 필요하다.
2. **저장 설정**에서 쓰기 가능한 폴더와 prefix/다음 번호를 확인한다. 경로는 자동 저장하고 prefix/번호는 적용한다.
3. 메인에서 **Zipy만 선택**하고 logging을 누른다. 현재 CAN/Diag를 포함한 실제 기록은 지원하지 않으므로 함께 선택하면 시작 전 안내하고 번호를 소비하지 않는다.
4. 기록 중에는 패킷 보기 창에서 최근 1,000건을 볼 수 있다. 창 닫기·표시 일시 정지·표시 필터는 파일 기록에 영향을 주지 않는다.
5. logging을 다시 누르면 정상 정지·파일 읽기/형식 검사·보관을 수행한다. 완료 파일은 지정 저장 폴더 루트에, 실패/미확인 파일은 표시된 실제 경로에 남긴다.

0패킷 파일도 정상 형식과 닫힘을 확인하면 보관할 수 있다. 이는 차량 통신 정상 판정과 다르다. 수신 판정 기준이 아직 없으므로 감시는 미설정으로 표시한다. 정상 정지가 확인되지 않으면 재시작과 정상 종료를 막는다. 이번 앱이 소유한 기록의 정지가 미확인이면 설정의 프로그램 종료를 다시 눌러 정상 정지를 재확인할 수 있다. 이전 비정상 세션의 자동 성공 처리·재연결·수동 복구 UI는 제공하지 않는다.

## 구현 내용

- 별도 Ethernet worker가 TShark와 dumpcap을 관리한다. UI는 명령·결과·유한 패킷 큐만 다룬다. 명령/세션 식별자와 늦은 응답 검사는 기존 제어 경로를 사용한다.
- TShark 버전·정확한 NPF NIC·검사 도구·경로/이름을 확인한 뒤 세션과 다음 번호를 원자 예약한다. 그 후에만 실제 기록 명령을 보낸다. 예약 뒤 시작 실패/취소에는 번호를 되돌리지 않는다.
- 선택한 NIC 하나, 명시적 pcap/pcapng, 이름 해석 끄기, 원본 저장과 필드 출력, stdout/stderr 지속 소비를 사용한다. 일반 기록에는 표시 필터나 시험용 캡처 필터를 붙이지 않는다.
- 시작 안내·형식/인터페이스 헤더·소유 프로세스 생존을 함께 확인한다. 0패킷 상태에서도 준비를 확인하며, 파일 존재나 PID만으로 기록 중으로 승격하지 않는다.
- 숨김 전용 콘솔의 Ctrl+Break로 소유 TShark/dumpcap에 정상 정지를 요청한다. 종료와 출력 EOF를 확인한 뒤 capinfos로 전체 파일을 읽고 실제 형식·패킷 수를 검사한다.
- 검사한 파일의 크기·수정 시각·파일 식별자가 바뀌지 않았을 때만 교체 없는 이동으로 보관한다. 기존 최종 파일이 생겼거나 검사/이동이 실패하면 기존 파일과 작업 파일을 유지한다. 이동 전 의도·이동 후 실제 경로를 DB에 남긴다.
- Windows Job Object로 worker와 자손을 소유한다. 정상 정지에는 강제 종료를 사용하지 않는다. 앱 비정상 종료의 자원 정리는 별도이며, 부분 파일과 미완료 DB 기록을 정상 완료로 바꾸지 않는다.
- 관측 요약 누락·파서 오류와 원본 기록 상태를 구분한다. 요약 큐가 차도 출력을 계속 소비하고 누락 수를 알린다. 차량 감시 기준을 임의로 만들거나 수신을 정상 판정하지 않는다.
- 개발자로그는 기본 OFF를 유지한다. 켜면 실제 명령 결과, worker/TShark PID, 도구/NIC/경로/형식, 요약 누락, 정상 정지/EOF, 검사/보관 결과와 예외를 저장한다. 캡처 payload는 진단 파일에 넣지 않는다.

## 검증

장비 없는 자동 검사 **167개**, Ruff와 의존성 검사 통과. 메타데이터 IPv4/IPv6/MAC 선택, 헤더, 유한 큐, 충돌·파일 변경, DB 예약/최종 저장 실패, 시작 취소, 미확인 정지, 소유 자손의 잔류·종료 실패 응답을 포함한다. 기본 자동 검사에서 실제 NIC를 열지 않는다.

실제 도구 검증은 명시적 `--verify-ethernet` 명령으로 수행한다. 테스트마다 새 앱 데이터 폴더와 localhost UDP 포트를 만들고 `NPF_Loopback`에 시험 포트 필터를 제한한다. pcap과 pcapng 각각 0패킷, 5패킷, 재시작의 총 6세션에서 기록→정상 정지→전체 읽기→보관, 파일 수와 실시간 요약 수 일치, 인덱스 1~6/다음 7을 확인했다. ARP는 생성한 오프라인 파일을 읽어 MAC 주소 대체 표시를 확인한다. 물리 NIC/차량/사용자의 다른 트래픽을 취득하지 않는다.

`tests/hardware/verify_ethernet_ui.py`에서는 실제 앱의 설정·연결 확인·logging·개발자로그·패킷 표시를 연결해 localhost 8패킷을 기록했다. 표시 일시 정지/창 숨김 중에도 기록·요약 전달이 유지되고 재개 시 8건이 보이며 파일 보관과 정상 앱 종료가 성공했다.

최종 폴더 EXE도 Python 경로·환경 변수를 제거한 조건에서 기본 OFF·개발자로그 ON/OFF·검색 결과의 UI 전달·실제 localhost 6세션을 통과했다. [실제 캡처 결과](../../../outputs/stage3/ethernet_verification.json), [EXE 검사](../../../outputs/stage3/exe_verification_results.json), [UI 검사](../../../outputs/stage3/ui_result.json), [패킷 화면](../../../outputs/stage3/packets.png)에 근거를 남긴다. 실제 pcap 출력의 나노초 변형(nsecpcap)도 pcap 계열로 확인하고 검사 결과에 구체 형식을 저장한다.

현재 검증 조합은 Windows 11 x64, Python 3.14.7, PySide6 6.12.0, pywin32 312, TShark 4.6.9, Npcap 1.89다. 새 PC와 차량 NIC, 장시간/1GiB 이상, 대표 부하·드라이버 드롭·정확한 시간 동기화는 검증하지 않았다. G-E의 로컬 기능 경로를 확인한 단계이며 현장·부하 게이트 전체 통과를 뜻하지 않는다.

## 남은 기능

CAN/Diag의 실제 COM 바인딩·구간 BLF 기록은 시험 PC의 대표 cfg로 이어 검증한다. 직전 파일 이름 변경/삭제·수동 복구·차량 통신 판정은 후속 단계이며 해당 파일 관리 버튼은 비활성 상태다. `.cfg`나 기존 CANoe 창은 이번 검증에서 열거나 수정하지 않았다.
