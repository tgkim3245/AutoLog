# CANoe 연결 실패 분석 — 2026-10-26

제공 버그리포트의 식별 가능한 PC/업무 경로와 원본 진단은 Git 밖에서 관리한다. 아래는 원인을 판단하는 데 필요한 비식별 요약이다.

## 확인한 사실

- 앱 1.0.0, Windows 빌드 26200, 64비트 프로세스. 실제 연결한 CANoe는 19.2.76 /pro다. 환경 목록에는 15.6.6도 있다. 설치/파일명만으로 의도한 RBS 버전을 단정하지 않는다.
- 2026-10-26 07:16:57~07:25:37(KST) 내 진단 224건, 앱 실행 2회, CAN 연결 오류 8회다. ZIP CRC 및 manifest의 235,034 bytes/SHA256이 일치했다.
- 독립 COM 창 생성과 can.ini 준비, Configuration.Open 완료, LoggingCollection.Count=2까지 확인됐다. 재시도 중 Measurement.Running=True도 관측됐다. 이 사실만으로 실제 차량 메시지 수신/라이선스 전부 정상/무손실을 증명하지 않는다.
- 첫 실패 07:21:13, 마지막 07:25:05의 예외 위치는 1.0.0 adapters/canoe.py의 connect에서 읽는 item.Name이다. 외부 HRESULT는 DISP_E_EXCEPTION(-2147352567), 서버 scode는 E_NOTIMPL(-2147467263, 0x80004001)이다.
- CANoe 창을 재생성한 뒤에도 같은 오류가 반복됐다. 이 보고서에서 앱 기록 시작 시도는 확인되지 않았다.

## 원인과 범위

앱이 로깅 블록의 표시 이름(Name)을 모든 환경에서 읽을 수 있다고 가정했다. 제공 환경은 그 속성에 미구현 오류를 반환해, RBS가 이미 열린 뒤에도 전체 연결을 실패로 처리했다. 이 로그의 직접 원인은 Name 조회를 필수로 다룬 앱 호환 문제다. 모든 19.2.x 또는 특정 차량에서 항상 발생한다고 일반화하지 않으며, 실제 블록 종류/프로젝트/서버 구현 차이는 원본 환경에서 추가 확인할 수 있다.

E_NOTIMPL 의미는 [Microsoft COM 오류 문서](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-1)를 따른다. 버전 선택이나 RBS 호환 실패와 달리 이번 기록은 Open 완료 후 속성 접근 실패다.

## 1.0.1 수정과 검증

Name의 미구현/미지원 멤버/속성 부재만 선택적으로 처리한다. Logging 1/2 번호를 표시하고 내부 식별용 Name은 알 수 없음으로 보존한다. 표시용 번호 이름으로 같은 출력 경로를 서로 다른 블록인 것처럼 만들지 않는다.

블록 수/순서·필수 FullName·선택/소유 출력 경로·Trigger/측정 상태 검사는 유지한다. RPC/권한/기타 COM 오류나 필수 FullName 오류는 전파한다. 이름 없는 다중 블록에서 수동 파일명을 바꾸면 다시 연결해야 한다. 단일 블록의 안전한 수동 변경과 소유 출력의 정상 복구/trigger 번호 정규화는 검증된 범위에서 허용한다.

제공 예외와 같은 COM 대역을 만들어 1.0.0의 동일 Name 조회 실패를 재현한 후 수정했다. 번호 표시, 새 COM 프록시, 반복 구간 기록/정지/BLF 검사, 동일 경로 모호성, 순서/개수/경로 변경, RPC/권한 오류와 필수 속성 실패를 회귀 검사한다. 실제 업무 cfg·물리 장비를 열거나 수정하지 않았다. 1.0.1을 해당 PC에서 다시 연결하고 짧은 기록·외부 reader 확인 후 새 버그리포트로 결과를 확인해야 한다.
