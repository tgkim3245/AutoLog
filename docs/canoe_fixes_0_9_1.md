# AutoLog 0.9.1 — CANoe 현장 준비 오류 수정

2026-10-19 · 실장비를 재연결하지 않고 확인 가능한 코드 오류와 안내·진단을 수정했다. 실제 라이선스 CAN/Diag 구간 기록은 아직 성공 검증하지 않았다.

## 확인한 사실

- 같은 실행에서 내보낸 두 버그리포트의 ZIP CRC와 manifest 크기/SHA256을 검증했다. 첫 리포트 134개 레코드는 두 번째 159개 레코드의 정확한 앞부분이다. 서로 다른 실행의 독립 재현 두 건이 아니다.
- CAN과 Diag는 CANoe 19.3.118 /pro CAN.LIN의 **서로 다른 PID**에서 각 cfg와 BLF 블록을 찾았다. 두 시도의 시작 준비에서 `Logging block changed`가 발생했으며 `start` 명령은 전송되지 않았다. 기존 로그에는 이 검증 당시 관측 블록의 세부 비교가 없어 실제 교체와 정상적인 COM 모델 갱신을 구별할 수 없다.
- 사용자는 CANoe F9 측정도 실패했다고 확인했으며 Write 오류는 `CAN (available)`, `Ethernet (missing)`, `Measurement was halted`였다. 대표 CAN cfg에는 Ethernet 네트워크와 DoIP 관련 구성이 있다. CAN 채널 매핑만으로 이 옵션 요구가 해결되지는 않는다. 옵션의 미보유·비활성·라이선스 인식 문제 중 어느 원인인지는 이 오류만으로 확정하지 않는다.
- 기존 채널 조회는 `bool(Configuration.DistributedMode)`를 사용했다. 설치된 공식 CANoe 19 타입 라이브러리의 `DistributedMode`는 `IDistributedMode` 객체이며 로컬 상태에서도 객체 자체는 참이다. 로컬 장비까지 원격으로 처리해 XL 조회를 생략하는 오류를 대역 재현했다.

업무 cfg·원본 리포트·장치 시리얼·개인 경로는 Git에 넣지 않는다.

## 수정

1. **로컬/원격 판정**: `RTServer`와 `Connected`를 읽는다. 서버 지정이 없고 연결 값이 0일 때만 로컬 XL 매핑 조회로 진행한다. 원격 서버 지정·연결 또는 API/형식 오류는 확인 불가다. 기억한 원격 서버가 남은 미연결 상태도 보수적으로 로컬 인증에서 제외한다. 원격 Connect/Disconnect나 매핑 변경은 호출하지 않는다.
2. **대기 중 블록 재조회**: 같은 cfg에서 COM identity만 바뀐 경우, 전체 블록 개수·순서·이름/출력 경로와 선택 블록의 파일 옵션이 연결 당시와 일치하고 동일 후보가 하나일 때만 새 핸들을 사용한다. 측정 준비 중 모델 갱신을 허용하기 위한 범위다. 실제 이름/경로/옵션/순서/개수 변경과 모호한 선택은 차단한다. 출력 적용 이후·기록 중 객체 교체는 기존처럼 차단하고 스냅샷을 보존한다. 영구 블록 ID API가 없어 완전히 같은 메타데이터로 대기 블록을 삭제·재생성한 경우는 논리적으로 같은 선택으로 취급될 수 있다.
3. **측정 안내**: 한/영/중으로 `이 cfg의 채널 매핑·필요한 모든 버스 옵션 라이선스 → F9 → Trace 수신 → 연결 재확인`을 안내한다. BLF 블록 선택이나 Zipy 해제가 CANoe cfg의 Ethernet 요구 사항을 없애지 않는다는 점은 사용자/현장 문서에 기록했다. 연결마다 팝업을 추가하지 않는다.
4. **오류 근거**: 명령 실패의 action·CANoe PID·현재 cfg·측정 실행·선택 블록 개수/이름/출력/trigger 상태, 블록 검증의 기대/관측 정보를 개발자로그에 남긴다. 측정 대기에서는 `UI.Write.Text`의 마지막 16 KiB 중 마지막 버스 옵션 오류 그룹만 최대 18줄·누락 옵션 16개로 제한해 읽는다. 일반 CAPL/Trace 내용은 저장하지 않으며 Clear/Copy/출력 파일 활성화는 호출하지 않는다. API가 없으면 비치명적 확인 불가다.

Write 창은 **과거 기록**이다. 안내에도 이전 시도일 수 있음을 표시하고 현재 라이선스 상태나 실행 중 측정의 실패 판정으로 사용하지 않는다. 실제 cfg·CAPL·하드웨어·라이선스를 자동 편집하거나 측정을 시작/정지하지 않는다. 두 cfg의 독립 창 연결 정책은 유지한다.

## 검증

- 전체 자동 검사 **454개 통과(29.56초)**, Ruff·pip 의존성·diff 공백 검사 통과.
- 실제 COM 형태의 로컬/원격 모드 대역, 원격 지정 미연결/상태 오류에서 로컬 조회 금지, 채널 기준 비교를 확인했다. 새 모드 객체로 기존 하드웨어 기준 검사가 실행된다.
- 대기 중 동일 블록 객체 갱신과 이전 핸들 단절 후 구간 시작/정지·원래 출력 옵션 복구를 대역으로 검증했다. 블록 변경/중복/순서·개수·옵션 변경, 출력 소유 중 동일 메타데이터 객체 교체는 차단한다. 다른 블록 trigger를 조작하지 않는다.
- 측정 실패의 `Ethernet (missing)` 오류 수집·이전 기록 표시, 일반 CAPL/시스템 출력 제외, 대기 안내 세 언어 전달, 실행 중 옛 오류 미조회와 Write API 부재를 검사했다. 실패 준비에서 다음 번호/파일은 예약하지 않는다.
- 실제 CANoe 인스턴스 생성·F9·차량 통신·VN 조회·라이선스 변경·원본 cfg 변경은 수행하지 않았다. 다음 현장 검증은 [라이선스 PC 절차](licensed_canoe_validation.md)를 따른다.

- Windows 글꼴을 로드한 Qt offscreen에서 한/영/중 측정 안내·옵션 오류 기록을 렌더링해 확인했다. 690×712 논리 크기에서 안내가 줄바꿈되고 가로 스크롤이 생기지 않는다. 긴 CAN/Diag 카드는 기존 세로 스크롤로 접근한다. 로컬 근거는 `Downloads/AutoLog_Builds/canoe-fixes-0.9.1/ui/`의 PNG·JSON이다.

## 배포 확인

- 변경 없는 소스 커밋 `5a2c3fe2848cebef56080b253b7771858fcb3d13`에서 `build.cmd --no-pause`로 `AutoLog-0.9.1_20261019_210152`을 만들었다. 위치는 로컬 `Downloads/AutoLog_Builds/AutoLog-0.9.1_20261019_210152/`다.
- 배포 ZIP은 **52,936,412바이트**, SHA256 `08ef5e96438de05d5939d7460511981ab705d854ec906d2283dcd9b112552cb4`다. EXE SHA256은 `653b51319f8e13d4fe98b09e480693551ba78375e63e5fa78adfe458af8a44cb`다. ZIP 전체 CRC·압축 해제 EXE 해시와 제품명/제품·파일 버전 0.9.1을 확인했다.
- 개발 Python 변수/경로를 제거한 환경에서 압축 해제 EXE의 중국어 설정 복원·모의 기록/정지·정상 종료·실제 네트워크 목록 조회를 통과했다. 이 실행의 EXE 옆 개발자로그 85개 레코드에 ERROR/CRITICAL은 없었다. 근거는 배포 결과 `verification/result.json`이다.
- EXE 아카이브에 CANoe 어댑터·수정한 하드웨어/측정/준비 진단·worker 모듈이 포함됐고 COM mutex 의존 파일도 포함됐다. 빌드 PC에는 Vector XL DLL이 없어 기존과 같이 분석 단계에 미발견 메시지가 있었으며 실제 VN 조회를 대신 통과 처리하지 않는다.
- 이번 배포에서 실제 CANoe 측정·장비 로깅은 수행하지 않았다. 앞선 0.9.0의 localhost 성능 수치를 새 버전의 차량/CAN 성공 근거로 승계하지 않는다.
