# 대표 CAN/Diag 구성 호환성 재검토

2026-10-18 · AutoLog 0.5.0의 실제 프로젝트 적용 전 검토.

**판정: 0.5.0을 대표 두 구성의 동시 로깅에 그대로 적용할 수 없다. 독립 COM 연결 게이트는 현재 PC 설정에서 실패했고, CAN 파일명 자동 증가도 현재 사전 검사를 통과하지 못한다.** 실제 기록·정지 게이트는 측정/라이선스 준비 후 별도 수행해야 한다.

업무 원본 .cfg·CAPL·데이터베이스·전체 경로·출력 파일명·해시는 Git에 포함하지 않는다. 로컬 상세 근거는 `Downloads/AutoLog_Builds/cfg-review-20261018/canoe-readonly.json`에 보관했다. 아래는 제품 개발에 필요한 구조와 동작만 요약한 것이다.

## 확인 범위

- 제공된 두 .cfg의 텍스트 구조, 기존 기록·트리거와 주요 데이터베이스/CAPL 참조를 읽었다. 확인한 직접 DBC·CDD·CAPL/CBF 참조 파일들은 존재했다. 전체 의존 파일, CAPL 컴파일, 장비 채널과 실제 수신 검증을 대신하지 않는다.
- 설치된 CANoe 19.3.118에서 CAN 구성을 열고 COM 속성을 읽었다. 다음 연결이 같은 구성을 반환하는 것을 확인한 뒤 교체하지 않고 중단했다.
- 그 뒤 이번 검토가 생성한 창의 측정 정지·미수정 상태를 확인하고, 동일한 검사 창에서 Diag를 순차로 열어 COM 속성을 읽었다. 두 구성을 동시에 연결한 실증이 아니다.
- Measurement.Start/Stop, Trigger.Start/Stop, CAPL 실행과 시스템 변수 쓰기를 하지 않았다. 원본 두 .cfg는 전후 SHA-256이 일치했다. 검토용으로 생성한 미수정·측정 정지 창만 저장 없이 닫아 초기 데스크톱 상태로 정리했다.

## 발견한 구현·환경 차이

1. **독립 COM 연결 실패 (G-C1).** 첫 번째 DispatchEx는 새 CANoe를 만들었지만 두 번째 DispatchEx는 첫 번째 CAN 구성을 반환했다. 0.5.0의 새 구성 보호 검사가 Diag Open을 막아 CAN 구성을 덮어쓰지 않았다. 같은 ProgID를 대상별 프로세스에서 호출한다는 사실만으로 독립 창이 보장되지 않는다.
2. **CANoe 설정의 영향.** 설치된 CANoe 19의 `can.ini`에서 `SingleCOMClient=0`을 확인했다. 같은 파일의 Vector 설명은 이를 켰을 때 후속 COM 클라이언트별 새 인스턴스를 허용하지만, 다른 COM 클라이언트 및 ActiveX/.NET 패널에서 부작용이 생길 수 있다고 안내한다. 이번 검토에서는 이 전역 설정을 바꾸지 않았다. 지원할 연결 방식은 이 설정의 영향과 프로젝트의 실제 패널 동작까지 포함해 결정·검증해야 한다.
3. **CAN 자동 파일명 증가.** CAN 블록은 트리거 후 자동 번호 증가를 사용한다. 0.5.0은 이를 감지하면 기록 준비를 거부한다. 현재 그대로 사용하려면 CANoe에서 해당 옵션을 수동으로 해제해야 한다. 자동화하려면 선택 블록의 파일명 관련 속성만 구간 중 관리하고, 변경/복구와 사용자 수동 편집 충돌을 검증하는 작업이 추가로 필요하다.
4. **기존 CAPL과 제어 충돌.** CAN 프로젝트에는 기존 로깅 버튼 이벤트에서 전역 startLogging()/stopLogging()을 호출하는 CAPL이 있다. 다른 라이브러리에도 경로 변경/정지 함수가 존재하지만 모두 실행되는 것으로 단정하지 않는다. AutoLog 기록 중 기존 버튼·자동시험을 함께 조작하면 여러 블록과 내부 버튼 상태가 어긋날 수 있으므로 공존 동작을 실제 시험해야 한다. 이 CAPL을 원본에서 삭제·수정하지 않았다.
5. **화면 표시 보완.** 0.5.0은 선택 목록에 주로 FullName을 표시한다. 실제 CANoe 블록 이름인 CAN_Logging/ETH_Logging/Logging과 확장자도 함께 보여 대상 선택을 명확히 해야 한다.
6. **현재 취득 환경.** 실제 실행 버전 문자열은 View Only였다. 라이선스/VN 장비를 준비한 환경의 측정 가능 상태 확인이 남아 있다. 이번 결과는 구성 열기와 속성 조회이며 실제 BLF 기록 성공을 뜻하지 않는다.

## 수정·시험 순서

1. 독립 COM 연결 방식을 확정한다. 두 참조의 구성이 다른지, 한쪽의 출력/기록 조작이 다른 쪽에 영향을 주지 않는지 먼저 검증한다. 전역 can.ini 변경은 일반 앱 실행 중 자동 조치로 넣지 않는다.
2. 실제 이름·형식·후보 적합성과 누락/교체된 선택을 UI에 표시한다. 기존 관리 창의 구성을 바꾸는 경우도 측정/기록 정지·사용자 편집 보존을 확인한다.
3. CAN의 파일명 증가 정책을 AutoLog의 공통 번호 정책과 맞춘다. 원본 Save 없이 경로/파일명 적용, 필요 시 구간 한정 옵션 관리·복구를 실증한다.
4. 라이선스/장비가 준비되면 CAN 단독 3회, Diag 단독 3회, CAN+Diag 순으로 기록·정지·BLF 판독·측정 유지·원본 해시를 확인한다. 그 뒤 Zipy 포함 조합과 기존 CAPL 제어의 공존을 검증한다.

이 검토는 [구현 계획](implementation_plan.md)의 IMP-03/08 현장 게이트와 [5단계](development_stage_5.md)의 미검증 항목을 구체화한다. 0.5.0의 장비 없는 검사 250개와 Ethernet 실증은 이 CANoe 게이트 실패를 상쇄하지 않는다.
