# 개발 기록

## 2026-10-20 — 공식 배포용 사용자 가이드와 자동 포함

- 과거 개발 초안을 현재 동작 기준의 오프라인 HTML 사용자 가이드와 START_HERE 배포 안내문으로 정비했다. Defender의 CAPLcompExec.exe·CANoe64.exe 허용 앱 등록을 첫 화면·초기 준비에 명시하고 회사 정책/다른 설치 경로·CANoe 재시작·재컴파일 순서를 포함했다.
- CAN/Diag·Zipy 연결, 기록·파일/복구·감시·버그리포트·업데이트와 실제 확인 범위를 정리했다. 소프트웨어는 0.9.2를 유지하고 문서 개정은 2026-10-20.1로 관리한다. 관리 원본·CHANGELOG·AGENTS/개발 규칙을 연결해 이후 작업에서도 함께 갱신한다.
- 빌드 전 가이드 적용 버전·원본·개정/날짜·치환자 검증, EXE 폴더/ZIP 자동 포함, build_info의 문서 개정·크기·해시 기록을 추가했다. 실제 배포/화면 확인 결과는 완료 후 이 기록에 덧붙인다.
- 전체 자동 검사 480개(29.44초)와 Ruff·diff 검사를 통과했다. 추가 9개 검사는 문서 누락·미검토 SW 버전 차단과 실제 ZIP 포함/해시 대조를 포함한다. QtWebEngine 오프라인 렌더링으로 표지·Defender/연결 절차·문제 해결·하단과 480px 폭을 확인했으며 가로 넘침·미치환 텍스트가 없었다. 근거는 로컬 `Downloads/AutoLog_Builds/user-guide-2026-10-20.1/visual-qa/`에 보관했다.

## 2026-10-20 — Diag CAPL 컴파일 쓰기 차단 원인 확인

- Diag 수동 기록 실패는 CBF 쓰기 거부였다. Defender 이벤트 1123에서 10:33:24의 `CAPLcompExec.exe` 차단 두 건과 10:31:30의 `CANoe64.exe` 차단을 해당 프로젝트 경로와 대조했다. 읽기 전용이 아닌 파일 속성·사용자 ACL과 유효한 Vector 실행 파일 서명도 확인했다.
- AutoLog 코드/버전/EXE, 원본 cfg/CAPL/CBF, Defender 정책은 변경하지 않았다. 정확한 Vector 실행 파일 허용 후 CANoe 재시작·재컴파일·수동 기록·AutoLog 순서로 재시험하도록 [환경 조치 안내](canoe_capl_compile_troubleshooting.md)에 기록했다. 해결 후 실제 Diag 시험은 아직 수행하지 않았다.

## 2026-10-20 — CANoe 출력 적용 후 시작·복구 차단 수정 (0.9.2)

- 새 현장 버그리포트 432개 레코드의 ZIP CRC·manifest 크기/SHA256을 검증했다. CAN 측정 실행과 `CAN_Logging` BLF 선택을 확인했으나 출력 설정 직후 COM 객체 비교로 configure와 rollback이 실패했다. CAN start 명령은 전송되지 않았다. 사용자는 수동 기록 성공을 확인했다.
- 프로젝트 패널의 `Logging` 버튼 → `Logging::logging_btn` → CAPL의 `startLogging()`/`stopLogging()` 연결을 읽기 확인했다. AutoLog는 해당 버튼 대신 선택한 BLF 블록을 직접 제어한다. 버튼 색/토글 내부 상태와 AutoLog 기록 상태는 동일하지 않다.
- 0.9.1의 대기 중 핸들 갱신만으로는 충분하지 않았다. 모든 단계에서 cfg·선택 인덱스·전체 블록 개수/순서/이름/경로와 소유 출력 경로·파일 옵션을 각 단계에 맞게 검증하도록 수정했다. IUnknown/IDispatch/Python 객체 identity는 판단 기준에서 제거했다. 외부 경로/구성 변경과 모호한 블록은 계속 차단한다.
- 매 조회마다 다른 COM 프록시/IUnknown을 반환하는 대역으로 구버전 0.9.1의 같은 오류를 재현했다. 수정 후 3회 구간 기록·조회·정지·BLF 검사·원래 출력/옵션 복구와 다른 블록 미조작을 확인했다. 전체 471개(30.30초), Ruff·pip·diff 검사 통과. 실제 CANoe 측정은 자동 실행하지 않았다. [분석·수정·배포 범위](canoe_fixes_0_9_2.md)를 따른다.
- 깨끗한 소스 `30e41f7`에서 `AutoLog-0.9.2_20261020_105034`을 빌드했다. ZIP 무결성·해시·버전, 압축 해제 EXE의 중국어 설정/모의 구간/정상 종료/NIC 목록·오류 없는 진단 89개를 확인했다. EXE에 포함된 어댑터 코드를 추출해 같은 프록시 대역의 3구간 검사도 통과했다. 실제 장비 측정과는 구분한다.

## 2026-10-19 — 현장 CANoe 준비 오류 수정 (0.9.1)

- 두 버그리포트가 같은 실행의 누적 로그임을 확인했다. CAN/Diag는 서로 다른 CANoe 19.3.118 PID에 연결됐으며 구간 시작 전 블록 검증에서 차단됐다. 사용자가 직접 확인한 CANoe 측정 오류는 `CAN (available) / Ethernet (missing)`이었다. 채널 매핑 오류로 단정하거나 실제 CAN 기록 성공으로 등록하지 않는다.
- `DistributedMode` COM 객체 자체의 참/거짓으로 원격 여부를 판단하던 오류를 수정했다. 실제 `RTServer`/`Connected` 속성을 읽으며 원격 지정·연결 또는 상태 조회 불가는 로컬 매핑으로 인증하지 않는다.
- 대기 중 CANoe 모델이 갱신된 경우 같은 cfg·블록 목록/순서·이름/출력·선택 옵션과 유일성을 대조해 핸들을 다시 얻는다. 출력 소유/기록 중 객체 교체나 실제 선택 변경은 계속 차단한다. 검증 실패의 기대/관측 정보와 명령 실패 시 측정·선택 블록 상태를 기록한다.
- 한/영/중 측정 준비 안내에 매핑·필요 버스 옵션 라이선스·F9·Trace·재확인을 명시했다. Write 창에서 버스 옵션 오류 그룹만 읽어 진단에 남긴다. 과거 기록임을 표시하고 현재 라이선스 판정에는 사용하지 않는다. cfg·매핑·라이선스를 자동 수정하거나 측정을 실행하지 않는다.
- 자동 검사 454개, Ruff, 의존성 검사와 diff 공백 검사를 통과했다. 실장비 재시험은 수행하지 않았다. 분석·제약·배포 근거는 [상세 수정 기록](canoe_fixes_0_9_1.md)에 관리한다.
- 깨끗한 소스 `5a2c3fe`에서 `AutoLog-0.9.1_20261019_210152`을 빌드했다. ZIP CRC·해시·버전, 압축 해제 EXE의 중국어 설정/모의 기록·정상 종료/NIC 목록과 진단 85개 레코드 오류 없음을 확인했다. 새 CANoe 수정 모듈의 배포 포함도 확인했다. 현장 CAN 재시험과 구분한다.

- 작은 화면 스크롤·창 제한·긴 입력 줄바꿈, 최근 활동 경고/오류 필터·원문 상세 복사, 검증한 압축 내보내기 이후의 DB 이력 정리를 추가했다. 실패·미완료·미확인 작업과 캡처 파일/다음 번호를 보존한다.
- dumpcap 직접 기록과 TShark 후행 해석을 분리했다. 30초/5,000 pps/150,000개 대조와 해석기 중단 후 15,000개 보존, pcap/pcapng 6회·감시 1,220개를 실제 localhost에서 확인했다. 물리 NIC·CANoe 측정은 실행하지 않았다.
- 최종 자동 검사 429개(27.61초)·Ruff 통과, 한/영/중 100~200% Qt 렌더링을 확인했다. 새 의존성 python-can/wrapt와 라이선스·교체 가능한 소스 패키징을 반영했다. [상세 변경·검증](usability_update_0_9_0.md), [개선 반영 상태](improvement_backlog.md), [CANoe 환경별 검증표](canoe_support_matrix.md)를 따른다.
- 깨끗한 소스 `9d67075`에서 `AutoLog-0.9.0_20261019_174756`을 빌드하고 ZIP CRC·해시·버전을 확인했다. 압축 해제 EXE의 중국어 프로필·모의 기록·정상 종료·NIC 조회·EXE 옆 진단과 실제 localhost 캡처 6회를 통과했다. 새 채널 기준이 있는 프로필을 실제 0.8.6 EXE가 읽는 설정 호환성도 확인했다. 해시·로컬 근거는 상세 변경 문서에 남겼다.

## 2026-10-19 — 화면 간소화·NIC 수신 그래프·중국어 (0.8.5)

- 요청 순서에 따라 설치/복구·다시 찾기·버퍼 선택 제거, 캡처 로그 폴더 열기, 버그리포트 대조/검증, 수신 그래프, 한/영/중 단일 토글, CAN·Zipy 기본 선택, 메인 큰 제목/상태 배지와 설정 종료 버튼 제거를 구현했다. TShark는 직접 선택하며 버퍼는 기존 설정과 관계없이 64 MiB로 고정한다.
- 실제 기존 버그리포트는 압축과 이후 원본 증가 때문에 크기가 달랐으며 스냅샷 원문 SHA256이 일치했다. 새 ZIP은 파일별 원본 크기·해시 목록, CRC/재읽기 검증을 포함한다. 기록 중 내보내기와 회전 백업·정상 JSONL 보존도 검사했다.
- 자동 검사 **386개** 및 Ruff·diff 검사를 통과했다. 실제 Windows 어댑터 12개의 목록·수신 pps 그래프와 한/영/중 화면 렌더링을 확인했다. 압축 해제 EXE 검사에서 중국어 기록을 차단하는 기존 언어 검증을 발견해 수정하고 세 언어의 시작·정지·번호 보존 회귀 검사를 추가했다. [상세 변경·검증](ui_update_0_8_5.md)을 따른다. CANoe 실제 측정·차량 부하 검증은 기존 잔여 범위를 유지한다.
- 최종 배포 `AutoLog-0.8.5_20261019_000941`을 소스 `10bb1ac`의 변경 없는 상태에서 빌드했다. ZIP CRC·압축 해제 EXE 해시/버전과 Python 개발 환경 없는 PATH에서 중국어 프로필·모의 기록/정지·정상 종료·실제 NIC 12개 조회를 확인했다. EXE 옆 개발자로그 84개에 ERROR/CRITICAL이 없었다. 해시와 근거 위치는 위 상세 문서에 남겼다.

## 2026-10-18 — cfg마다 CANoe 자동 독립 연결 (0.8.4)

- cfg별 독립 연결을 필수 동작으로 바꾸고 연결 모드 설정창·켜기/복구 선택을 제거했다. 최초 연결에서 필요한 Vector 설정을 원본 백업 후 자동 적용한다. 이전 기본 모드 CANoe가 실행 중일 때만 작업 보관·전체 종료 후 재연결을 안내한다.
- 두 worker의 설정/COM 생성을 프로세스 간 잠금으로 직렬화하고, 요청마다 새 CANoe PID 하나와 선택한 cfg의 정확한 일치를 확인한다. 각 카드에 연결된 파일·PID를 표시한다.
- 자동 검사 379개 및 Ruff를 통과했다. 실제 두 cfg의 동시 worker 연결·역순 재연결, 실제 설정 버튼 두 개 연속 클릭을 각각 확인했다. 두 CANoe 프로세스·블록 1씩·원본 cfg SHA256 보존을 확인했으며 측정/Trigger는 실행하지 않았다. [수정 및 근거](canoe_independent_connection.md)를 따른다.

## 2026-10-18 — CANoe cfg별 연결 안내 개선 (0.8.3)

- 두 .cfg를 각각 다른 CANoe 인스턴스에서 열고, 각 구성의 기록 블록 하나를 제어한다는 동작을 연결 설정 안내에 명시했다.
- 기본 COM 연결이 두 번째 요청에 기존 창을 반환할 수 있는 이유, 적용 전 모든 CANoe 창을 닫아야 하는 조건, CANoe 설치 전체에 미치는 영향과 원복 방법을 분명히 했다. 설정 버튼과 연결 오류 안내의 이름도 cfg별 연결로 맞췄다.

## 2026-10-18 — CAN·Diag 설정 짝 표시 개선 (0.8.2)

- `%LOCALAPPDATA%\Auto_Log`와 `%LOCALAPPDATA%\VILLogging`의 설정을 새 `%LOCALAPPDATA%\AutoLog`로 한 번만 복사한다. 이전 기본 prefix만 새 이름으로 바꾸며 사용자 지정 경로와 설정은 보존한다.
- 이전 버전이 실행 중일 때 새 버전이 구버전을 조용히 앞으로 가져오는 대신 종료 안내를 표시한다. TShark 자동 검색은 두 이전 도구 폴더도 계속 확인한다.
- 빌드 산출물과 PC별 결과는 `.gitignore` 규칙으로 버전 관리에서 제외한다. 소스, 문서, 테스트와 배포 설정을 Git으로 관리한다.

## 2026-10-18 — 저장소 구조와 Git 관리 대상 정리

- 원격 연결과 첫 커밋은 있었지만 `README.md`만 추적 중이었다. 앱 소스, 기존 검사, 의존성 정의, 빌드 사양, 라이선스와 개발 문서를 프로젝트 관리 대상으로 정리했다.
- 실행 앱은 `src/vil_logging/`에 모은다. HTML 시안은 `docs/design/wireframe.html`, 시험 PC 확인표는 `docs/test_pc_setup.md`로 이동하고 관련 링크를 갱신했다.
- 사용하지 않는 빈 모듈·샘플·근거 자료 폴더의 `.gitkeep`과 이미 파일이 있는 폴더의 중복 `.gitkeep`을 제거했다. Git은 빈 디렉터리를 추적하지 않는다.
- `outputs/`의 이전 배포본·검증 근거·설치 파일은 로컬에 보존하고 안내 README만 추적한다. 캡처와 개발자로그, 가상환경은 제외한다.
- 첫 커밋 README의 혼합 인코딩과 현재 안내를 정리하고, 앞으로의 실행·빌드·Git 작업 절차를 문서화했다. 기존 커밋 이력은 다시 쓰지 않는다.
- Ruff 정적 검사, Python 56개 파일의 구문 검사와 로컬 문서 링크 116개 확인을 통과했다. 문서와 일부 Python 파일 끝의 중복 빈 줄도 정리했다. 앱 동작 로직 변경, EXE 빌드와 실제 차량·CANoe 캡처는 이번 정비에 포함하지 않는다.
