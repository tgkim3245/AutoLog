# CANoe 실제 기록 준비 점검

기준 SW 1.0.0 · 검토 2026-10-25

상세 실행·결과 기록은 [48 TC](vehicle_test_plan.md)를 사용한다. 이 문서는 CANoe 환경의 시작 전 점검과 파일 판정을 보완한다. 대역·타입 정보·연결 성공을 실제 측정·차량 취득 성공으로 처리하지 않는다.

## 시작 전

- Windows·앱 버전/빌드·CANoe 전체 버전·옵션 라이선스·Vector 드라이버/장비를 기록한다.
- 서로 다른 CAN·Diag cfg의 의존 파일, BLF 블록·실제 창/PID 대응을 확인한다. 같은 카드 재확인으로 중복 창을 만들지 않는지도 본다.
- CANoe가 열리지 않으면 등록 누락/손상 안내와 해당 버전의 공식 RegisterComponents를 확인한다. 독립 모드 준비에서 기존 창 종료를 요구하면 사용자 작업부터 저장한다.
- F9·컴파일·Trace와 실제 채널 매핑을 확인한다. 연결된 DBC가 기대 메시지의 CAN 번호와 일치하는지도 확인한다.
- 선택 블록의 기존 수동 기록만 정지하고 측정은 유지한다. 원본 cfg의 사용자 변경은 직접 저장한다.

## 구간과 데이터

CAN 단독 → Diag 단독 → 두 대상 → Zipy 포함 조합 순서로 시작한다. 최초에는 짧게 파일 완결을 확인하고 N 절차의 60초·10회 반복으로 넓힌다. 시작/정지/도구 정지/보관 완료 시각을 구분하고 세션 번호·각 파일 결과를 기록한다.

정상 정지 후 CANoe 측정을 유지해야 하며 다른 블록을 조작하지 않는다. 출력 이름 복구 보류와 실제 BLF 완결/보관 실패를 구분한다. 같은 cfg·블록에서 파일명만 수동 변경/자동 증가한 경우 연결 재확인이 매번 필요하지 않다.

BLF를 실제 reader에서 열어 프레임·CAN 번호·시간 구간·신호/진단을 확인한다. 첫 프레임이 측정 기준 0초가 아닐 수 있다. 구조 검사·completed·0프레임 유효 파일은 기대 수신 성공과 다르다. Diag 누락은 TC-20의 동일 버스 매핑·공통 구간·시간차 보정과 기준 자료로 확인한다.

## 이상과 종료

기록 중 CANoe 측정·선택 블록 중지나 응답 확인 실패가 확인되면 현재 정책은 **전체 선택 기록 정지**다. 정상적으로 닫힌 파일만 보관하고 실패 원인을 유지한다. 물리 CAN선 무수신은 측정/기록 도구가 유지되면 자동 감지하지 못할 수 있다.

메인 X는 정상 보관 요청이 아니라 전용 CANoe 종료·중단 구간 폐기다. 저장이 필요하면 먼저 메인 정지·보관을 마친다. 재실행에서는 이전 미완료 소유 파일을 정리하며 완료 파일·소비한 번호를 유지한다. 오류 재현은 정차/격리 조건과 승인된 기존 절차 안에서만 한다.

결과는 [환경별 검증표](canoe_support_matrix.md)에 버전·조합·실제 수행 범위를 추가한다. 업무 cfg·원본/진단·개인 경로는 Git에 넣지 않는다.
