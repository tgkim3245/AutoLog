# AutoLog 0.9.0 — 준비 상태·채널 기준·화면·캡처 개선

2026-10-19 · 높음/중간 개선 6건과 조건부 캡처 분리를 구현했다. 낮음 두 건인 전체 파일 이력 검색/페이지 이동과 버그리포트 환경 요약은 포함하지 않았다.

## 사용자 동작

- CAN/Diag 카드에서 `cfg 열림 → 측정 시작 대기 → 구간 기록 준비`를 구분한다. View Only, 블록 미선택·기존 기록 중, 채널 기준 불일치/조회 불가도 따로 표시한다. 메인에는 짧은 단계와 설정창에는 다음 조치가 표시된다.
- 조회 가능한 로컬 Vector XL 채널의 논리 CAN 번호·장치 이름·시리얼·물리 포트를 표시한다. 사용자가 시험 장치를 확인하고 **채널 기준 저장**을 누르면 cfg별 기준을 기억한다. 연결 및 시작 준비에서 비교하며 저장한 기준과 다르거나 확인하지 못하면 시작을 차단한다. cfg 변경은 이전 기준을 해제한다. 기준을 새로 저장하거나 명시적으로 해제할 수 있다.
- 원격/분산 CANoe, 가상 장치, API/드라이버 조회 실패는 확인 불가로 표시한다. 채널 조회는 읽기 전용이며 포트를 열거나 버스 활성화·송신·매핑 변경을 하지 않는다. 채널 일치는 차량 데이터 수신 성공을 뜻하지 않는다. 기록 중 매핑의 지속 감시까지 구현한 것은 아니다.
- [CANoe 버전·환경별 검증표](canoe_support_matrix.md)에 CANoe/라이선스/VN/드라이버/cfg·블록·연결/실제 BLF 결과를 구분한다. 현재 실제 라이선스 BLF 성공 행은 없다.
- 창은 화면의 사용 가능한 논리 크기에 맞춘다. 메인은 기본 폭 480px이며 작은 화면에서는 스크롤하고 좁은 헤더를 줄인다. 설정의 긴 입력 행은 필요하면 줄바꿈한다. 최근 활동에 전체/경고·오류/오류 필터와 선택 항목 원문·시각·상세 복사를 추가했다. 500건 상한은 유지한다.

## 캡처 경로

dumpcap이 선택한 NIC에서 원본 pcap/pcapng를 직접 기록한다. 별도 TShark는 같은 파일의 증가분을 표준입력으로 받아 해석한다. 읽기 스레드는 최대 64 KiB씩 전송하며 해석 지연의 역압력이 원본 기록 경로를 통과하지 않는다. 실제 메모리와 처리량은 도구·장치·부하에 영향을 받는다.

원본 dumpcap은 기존 정상 콘솔 정지·종료 코드·파일 전체 읽기 검사로 닫힘을 확인한다. 해석기는 원본 정지 후 최대 5초 동안 남은 데이터를 배출한다. 그 뒤에도 정체된 **읽기 전용 해석기만** 종료할 수 있다. 해석 오류·누락 수를 남기고 감시를 확인 불가로 표시한다. 해석기 오류만으로 완결된 원본을 폐기하거나 원본 손실로 판정하지 않는다. 원본 파일 검사 결과와 표시/관측 손실은 별도로 보존한다.

도구 경로는 직접 고른 `tshark.exe`와 같은 폴더의 `dumpcap.exe`·`capinfos.exe`를 확인한다. 캡처 버퍼 64 MiB, 원본 무필터 기본, loopback 검증 전용 필터 제한을 유지한다. [공식 dumpcap 설명](https://www.wireshark.org/docs/man-pages/dumpcap.html), [TShark 설명](https://www.wireshark.org/docs/man-pages/tshark.html)을 참고한다.

## 이력 정책

앱 시작 시 DB 소유 스레드에서 정리한다. 90일 초과 또는 이벤트 10,000건·완료 세션/완료 파일 작업 각 1,000건 초과가 후보이며, 최근 이벤트 500개와 완료 이력 각 100개는 최소 유지한다. 실패·미완료·활성 세션과 미확인 파일 작업 관련 이력은 보존한다. 이 예외 때문에 전체 DB 크기의 엄격한 상한을 보장하지 않는다. 새 채널 기준은 별도 확장 테이블에 두어 기존 v2 설정 JSON에 새 필드를 넣지 않는다.

프로필의 `history_archive/AutoLog_history_<UTC>_<고유번호>.jsonl.gz`에 후보 메타데이터를 독점 생성·압축하고 flush/fsync, 전체 재읽기 SHA256 대조를 통과한 뒤 한 SQLite 트랜잭션으로 정리한다. 내보내기/검증 실패 시 DB 삭제는 롤백한다. 캡처 파일·다음 번호·현재 설정은 변경하지 않는다. 압축 이력은 자동 삭제하지 않으며 DB의 빈 페이지는 다음 기록에 재사용한다. 앱 실행 중에는 정리를 반복하지 않아 기록 제어에 무거운 정리 작업을 끼워 넣지 않는다.

## 검증

- 최종 자동 검사 **429개 통과(27.61초)**, Ruff 통과. 내보내기 실패/재검증 실패 시 DB 보존, 미완료·미확인 작업 예외, 최근 최소 건수·중복 없는 시작 알림, 채널 기준 비교/시작 차단, 해석기 정체 시 파일 보존을 검사했다. CANoe 실제 측정은 실행하지 않았다. 최종 배포 결과는 아래에 별도로 기록한다.
- 실제 TShark 4.6.9: pcap/pcapng 각각 0패킷·5패킷·재시작 6회와 비IP ARP 읽기 통과. 통신 감시의 생성 localhost 패킷 1,220개 시험 통과.
- 30초·5,000 pps·512바이트: 150,000개 송신/저장, 84,000,024바이트 PCAP. 순번·내용 대조에서 누락/중복/내용 오류 0. 해석 150,000개·해석 오류 0, 최대 처리 지연 약 526ms. 소비하지 않은 화면 큐의 149,000건 누락은 원본 캡처 손실과 구분한다. 차량 성능 보장값이 아니다.
- 실제 해석기 장애 주입: 최초 5,000개 후 이 시험이 소유한 TShark만 종료했다. dumpcap 기록은 유지됐고 감시는 확인 불가로 전환됐다. 이후 10,000개를 더 보내 총 15,000개의 순번/내용·정상 원본 종료·capinfos 전체 읽기를 통과했다. 원본 크기는 2,800,024→8,400,024바이트로 증가했다. 도구별 CPU/메모리 스냅샷도 로컬 결과에 보관했다.
- 위 장애 시험의 5,000개 처리 후 스냅샷에서 dumpcap 누적 CPU 약 0.094초/최대 작업 메모리 약 10.3 MiB, 해석기 약 0.25초/98.3 MiB였다. 짧은 생성 트래픽·시작 비용 포함 측정으로 일반적인 CPU 비율/메모리 상한을 뜻하지 않는다.
- Windows 글꼴을 로드한 Qt offscreen에서 한/영/중 각각 100/125/150/200% 배율을 렌더링했다. 작은 사용 영역에서 메인 세로 스크롤·하단 동작 접근, 최종 200% 영문 가로 밀림 해소를 확인했다. 실제 다중 모니터 전환·새 PC 시험과 구분한다. 근거는 로컬 `ui-final/`의 PNG·JSON이다.
- 로컬 근거는 `Downloads/AutoLog_Builds/improvements-0.9.0/`의 `ethernet-1`, `monitoring-1`, `load-1`, `decoder-failure-1` 각 `result.json`이다. 생성한 loopback 트래픽만 사용했으며 물리 NIC·실제 CANoe 측정을 열지 않았다. 업무 원본·캡처·진단 로그는 Git에 포함하지 않는다.
- 채널 조회·비교·시작 차단은 COM/드라이버 대역 검사다. 실제 VN·라이선스 BLF·차량 고부하·60분·새 PC/오프라인 배포는 [현장 절차](licensed_canoe_validation.md)와 환경별 검증표로 확인해야 한다.

## 의존성

Vector XL의 구조체·읽기 조회 바인딩에 python-can 4.6.1과 wrapt 1.17.3을 추가했다. CAN Bus 인스턴스나 송수신 API는 사용하지 않는다. LGPL 고지·원본 링크와 교체 가능한 Python 소스 형태를 배포에 포함한다. Vector 드라이버 DLL과 Wireshark는 배포에 포함하지 않는다.
