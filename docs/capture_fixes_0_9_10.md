# AutoLog 0.9.10 — 종료·재실행과 Enter 이름 변경

2026-10-22. 사용자 제공 ZIP과 Windows 오류 기록을 읽고 파일별 검증을 수행했다. 실제 CANoe 측정/기록을 조작하거나 보안 설정을 변경하지 않았다. 진단 원문·캡처·업무 cfg·개인 경로는 Git에 넣지 않는다.

## 현장 근거

- ZIP CRC와 manifest 크기/해시 일치. JSONL 2,238건·3,692,724바이트·SHA256 `e0aaaae0b7668901c5b5fb9563f0987994f6a88f3f6b4859bb39e23010003f24`다.
- 0.9.9는 CAN+Diag+Zipy 연속 3구간을 포함해 역할 조합별 9구간을 정상 보관했다. Diag 원래 경로 복구도 정상 확인됐고 복구 보류 경고는 0건이다. 이전 Diag 반복 시작 수정은 이 현장 근거에서 성공했다.
- 마지막 새 구간은 세 대상 시작/조회까지 성공했고 10:38:06 이후 앱 로그가 끊겼다. Windows Application Hang 1002 / WER AppHangB1 1001이 10:38:17에 기록됐다. 사용자는 파일 저장 완료 후 X를 눌렀다고 설명했다. 해당 구간의 정상 정지·X 요청 로그가 없어 클릭 전달 여부나 구체적으로 멈춘 함수를 확정할 수 없다.
- 재실행은 이 구간을 미완료로 복원해 새 시작을 차단했다. 파일 유지 정리 시도도 파일 근거 token 변경으로 3번 거부됐다. 변경 중인 파일을 보호하는 검사를 없애지 않는다. 현재는 세 소스의 파일 잠금이 풀렸고 근거 token도 안정됐다.

## 수정

1. 화면이 multiprocessing Queue를 직접 읽는 경로를 제거했다. `get_nowait()`도 부분 전송/파이프 상태에 따라 내부 수신을 기다릴 수 있다. 전용 daemon 수신기와 최대 1,000건의 메모리 큐를 사용한다. 화면은 짧은 메모리 접근만 수행하며 IPC 수신기가 멈춰도 X 처리를 유지한다. 로컬 큐 초과는 오래된 화면 요약부터 버리고 세션별 누락 통계에 합산한다. dumpcap 원본 기록과 분리한다.
2. worker의 `release()`가 허용한 복구 보류를 pool 종료가 다시 강제 복구로 거부하던 모순을 수정했다. pool은 adapter에 release 검증을 요청하고 정지한 소유 출력으로 확인된 보류만 허용한다. shutdown 응답/진단을 먼저 소비·확인한 뒤 join해 worker가 가득 찬 응답 파이프에서 멈추지 않게 한다. 외부 편집/정지 미확인은 여전히 실패하며 자기 worker/job만 정리한다.
3. 화면 응답이 5초 이상 늦으면 thread stack을 지연 한 회당 한 번 순환 개발자로그에 기록하고 응답 복귀를 남긴다. 변수 값·패킷 내용은 포함하지 않는다. 현장 AppHang의 정확한 스택이 없는 한 위 잠재 경로 제거를 동일 원인의 실장 해결 증거로 간주하지 않는다.
4. 직전 파일 입력란의 Return/숫자 키패드 Enter를 기존 이름 변경 동작에 연결했다. 파일 처리/기록 중 잠금과 인덱스를 붙이지 않는 규칙은 유지한다. 복구의 상태 변경 오류는 CANoe 수동 기록 정지·새로 고침·재선택을 안내한다.

## 현장 파일 복구

실행 중인 AutoLog/dumpcap/TShark가 없고 각 소스가 독점 접근 가능한 것을 확인했다. 전체 읽기에서 BLF 두 개는 완전했고 PCAP은 15,352패킷 뒤 마지막 패킷이 잘린 오류였다. PCAP 검사 실패 때는 어느 파일도 먼저 옮기지 않았다.

SQLite 사전 백업 후 기존 RecoveryService로 완전한 BLF 두 개만 최종 폴더에 보관하고 원문 해시를 대조했다. 손상 PCAP 23,300,171바이트는 임시 원본을 그대로 보존했다. 해당 구간은 정상 취득 성공이 아닌 `failed/manual_review`로 정리하고 다음 번호 9와 이전 완료 구간·이력을 유지했다. 복구 후 새 시작을 막는 미완료 구간은 없다. 근거·DB 백업은 로컬 빌드 저장소 `field-recovery-0.9.10/`에 둔다.

| 대상 | 크기 | 구조 객체 수 | SHA256 | 처리 |
| --- | --- | --- | --- | --- |
| CAN | 17,259,530 | 567,301 | `41ecb939245c19bef16f62e8f49fe561b5823dc4d27aa9482959de3e9a9b25f9` | 완전한 BLF 보관 |
| Diag | 13,709,910 | 422,588 | `95ecf05270bc96c1831407515ff84c2a077a26ce5969cac430cf3c0bc1beebaa` | 완전한 BLF 보관 |
| Zipy | 23,300,171 | 마지막 패킷 잘림 | `53bca6122f72d9afdf0d4fd5f1448d782a2177c172e3b687ce3c47f06e7e1fa4` | 원본 유지, 정상 완료로 표시하지 않음 |

구조 객체 수는 디코딩한 CAN 프레임 수와 다르다. BLF 선언 객체 수와 실제 구조 객체 수의 차이는 별도로 유지한다. 복구 성공을 차량 무손실의 증거로 쓰지 않는다.

## 검증 범위

멈춘 IPC 수신 중 실제 Qt X 이벤트 처리, bounded 표시/세션별 누락 집계, 복구 보류의 정상 종료 수용과 외부 편집 거부, 저장 완료→X→재실행→새 기록, Return/Enter 단일 이름 변경과 잠금을 검사한다. Windows AppHang의 정확한 원인 확정·새 버전 실장 종료/재실행·차량 고부하/장시간 검증은 남아 있다.

전체 자동 검사 577개(61.45초), Ruff·의존성·diff와 문서 로컬 링크 283개를 통과했다. 종료 응답 미확인 시 정상 완료 거부, 표시 큐 누락의 세션별 합산/중복 합산 방지와 UI 지연 한 회당 스택 한 번 기록·복귀도 검사했다. 공식 가이드 2026-10-22.2의 12개 PC/작은 폭 뷰포트에서 Enter·종료·복구·검증 범위를 검토했다.
