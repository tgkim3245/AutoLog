# AutoLog 전체 검토 — 0.8.6

2026-10-19 · 검토 기준: 0.8.5 (`708b67b`) → 수정 버전 0.8.6.

**판정: 기본 앱과 Ethernet 경로는 구현·시험 근거가 있지만 전체 요구사항 완료 상태는 아니다. CAN/Diag의 독립 연결과 실제 구간 BLF 기록 성공을 구분해야 한다.** 확인한 버그와 문서 오류는 수정했고, 선택적 기능·UI 개선은 [별도 제안](improvement_backlog.md)에만 남겼다.

## 이번에 수정한 동작 오류

| ID | 재현 조건과 기존 문제 | 수정 및 검사 |
| --- | --- | --- |
| A-01 | 연결 확인 후 CANoe의 같은 번호에 다른 Logging Block이 들어오면, logging의 준비 단계가 기존 객체를 버리고 새 블록을 채택함 | 준비 전에 기존 cfg와 COM 객체 동일성을 검사한다. 변경 시 시작을 거부하고 명시적 연결 확인으로 다시 선택하게 한다. 교체/구성 변경 거부와 명시적 재연결을 COM 대역 검사로 확인 |
| A-02 | CAN 정지 미확인 중 Diag/Zipy는 보관 완료. 이후 정지 재시도 또는 X 종료 시 이미 이동된 작업 파일을 `not_created`로 덮어씀 | 이번 세션에서 보관 완료한 파일의 경로·검사 결과를 유지하고 파일 식별 정보를 재확인한다. 이미 보관한 파일은 다시 검사·이동하지 않는다. 복구 버튼·X 경로와 외부 파일 변경을 회귀 검사 |
| A-03 | TShark 미설치/잘못된 경로로 준비 실패 후, 실제 캡처가 없는데도 idle worker 때문에 X 종료가 거부됨 | idle/ready도 종료 가능한 상태로 인정하되 Windows Job에 녹화 자식 프로세스가 남아 있으면 계속 차단한다. 실제 worker로 없는 실행 파일 경로를 지정한 재현 검사 통과 |
| A-04 | 최근 활동 500건과 미완료 복구·품질 알림이 시작 시 512칸 알림 큐를 넘김 | 과거 500건은 하나의 묶음으로 전달한다. 이력·미완료·중단된 파일 작업을 함께 복원하는 조건에서 상태 알림 유실 없음 확인 |
| A-05 | CANoe 출력 복구가 남아 있는데 shutdown 응답을 기다리지 않고 worker를 정리하면 원래 경로/옵션의 메모리 스냅샷을 잃을 수 있음 | worker 종료 전 별도 복구 요청의 성공을 확인한다. 실패 시 worker와 스냅샷을 유지하고 정상 종료를 보류한다. 외부 경로 수정으로 복구가 거절되는 대역 검사 추가 |
| A-06 | TShark 자동 탐색을 제거한 뒤 개발용 `--verify-*` 명령들이 빈 경로로 도구를 찾아 실패함 | `--tshark`로 명시적 설치 경로를 전달한다. 누락 시 실행 전에 사용법 오류를 표시한다. CLI 전달 검사와 실제 localhost/오프라인 검증 4종 통과 |

앞의 대역 검사는 해당 실패 분기와 보존 정책을 확인한다. 실제 CANoe 측정·트리거 응답을 시험했다는 뜻은 아니다. 사용자 cfg·CAPL·can.ini를 이번 검토에서 변경하거나 CANoe 측정을 시작하지 않았다.

| 블록 선택 | `CanoeCapture.connect/prepare/_validate` | 기존 BLF 블록만 선택. CAN의 다른 PCAPNG 블록을 제외. 다른 cfg·블록 교체·미저장 변경을 보호. 이번 A-01 보완 |
| 기록 준비 | `prepare/configure` | 사용자가 측정 시작, 선택 Trigger 비활성 확인. 출력 경로와 자동 증가/분할 옵션 4개를 보관·변경·읽기 확인. 원본 cfg Save 호출 없음 |

| 시작 | `CanoeCapture.start` | 선택 블록 Trigger.Start, Active 및 정확한 임시 파일의 LOGG 헤더 확인. Ethernet 선택 시 먼저 기록 준비 후 CAN/Diag에 요청. 동시 시각 보장 아님 |
| 정지 | `CanoeCapture.stop` | 선택 Trigger.Stop, 비활성·파일 배타 접근 확인. Measurement.Start/Stop·CANoe 강제 종료 없음. 출력 설정을 복구하고 실패를 별도로 보존 |
| BLF 보관 | `storage/blf.py`, `publish_capture` | 스트리밍 구조·압축·객체 경계 검사 후 덮어쓰기 없는 이동. CAN 신호 해석이나 기대 프레임 수신 성공을 인증하지 않음 |
| 부분 실패 | `Runtime._query/_stop_real`, worker 분리 | 기록 중 한쪽 실패는 다른 기록을 유지. 정지 요청을 모두 보낸 뒤 기다림. 이번 A-02로 재시도 시 보관 결과 유지 |

설치된 Vector `Exec32/COMdev/CANoe.tlb`를 COM 인스턴스 생성 없이 읽어 `ILogging4`의 `FullName` 읽기/쓰기, `FileNameOptions`와 `ITrigger.Start/Stop/Active`, 파일명 옵션 4개의 존재를 확인했다. **타입 정보는 메서드 존재만 확인하며, 측정 중 속성 변경 가능 여부·파일 닫힘 시점·트리거 모드별 동작을 증명하지 않는다.** 온라인 도움말 본문은 이번 도구에서 접근되지 않아 동작 실증의 근거로 추가하지 않았다.

최근 실제 CANoe 실행 근거는 CANoe 19.3.118 **View Only** 상태의 구성 열기/조회다. 이번 검토는 라이선스 활성 상태를 새로 확인하지 않았다. 라이선스 PC에서 [실제 기록 체크리스트](licensed_canoe_validation.md)를 수행하기 전에는 “CAN 로깅 검증 완료”로 표시하지 않는다.

## 잠재적 문제와 운영상 한계

- TShark가 원본 저장과 실시간 해석을 함께 수행한다. 화면 요약 큐는 유한하지만 해석 CPU/출력 지연이 취득에 미치는 영향까지 제거하는 구조는 아니다. 대표 부하 실측 후 취득/해석 분리를 판단한다.
- pcap에는 드롭 통계가 없고 pcapng도 드라이버가 제공한 선택 통계만 읽는다. 통계 미제공을 손실 0으로 표시하지 않는다. 보관 완료와 기대 차량 데이터 수신은 다르다.
- 기존 cfg에는 CAPL 로깅 버튼·제어 경로가 있다. AutoLog 기록 중 이를 동시에 조작하면 블록·경로·시작/정지가 충돌할 수 있다. 현재는 재조회와 불일치 차단으로 보호하고 CAPL을 수정하지 않는다.
- `SingleCOMClient=1`은 AutoLog만의 설정이 아니라 해당 CANoe 설치의 전역 설정이다. 다른 COM 클라이언트·ActiveX/.NET 패널 조합은 현장 확인이 필요하다. 사용자 작업 중인 CANoe를 강제로 닫지 않는다.
- CANoe COM 호출이 외부 대화상자나 서버 정체로 막히면 시간 초과는 성공으로 처리하지 않는다. 복구될 때까지 worker 참조와 미완료 상태를 유지하는 정책이다.
- BLF 시작 헤더 확인 8초, 정지 닫힘 확인 28초, 구조 검사 110초는 구현 시간 제한이다. 실제 cfg의 버퍼/후행 기록과 큰 파일의 저장장치 성능에서 적절한지 확인해야 한다.
- 개발자로그는 약 25 MiB로 회전하지만 SQLite 세션/이벤트 DB는 자동 정리되지 않는다. 장기 사용 시 조회·디스크 증가를 측정할 필요가 있다.
- 개발자로그 폴더와 캡처 폴더에는 쓰기 권한이 필요하다. EXE를 읽기 전용 위치에 놓으면 진단 저장 실패를 표시하며 임의의 다른 경로로 숨겨 저장하지 않는다.

## 문서 정비

현재 기준인 요구사항·설계·제어 정책의 “실제 도구 미연동”, 개발자로그 체크박스/200줄/2개 언어 설명을 수정했다. 구현 계획의 오래된 최신 결과 링크와 파일명 예시도 바로잡았다. 과거 단계별 실패·성공 기록은 삭제하지 않고 그 당시의 근거로 유지한다. 설치 후보 문서는 과거 조사임을 표시했다.
