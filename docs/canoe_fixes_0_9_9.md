# AutoLog 0.9.9 — Diag 다음 기록 차단 수정

2026-10-22. 현장 리포트·완료 파일을 읽기 전용으로 분석했다. 외부 CANoe·측정·cfg·사용자 파일·번호를 변경하지 않았다. 실제 캡처·진단 원문·업무 cfg와 개인 경로는 Git에 넣지 않는다.

## 확인한 원인과 결과

ZIP CRC, manifest 크기·해시가 일치했다. JSONL 1,078건 / 1,392,774바이트 / SHA256 `1d11a9dee0227c805f5b9c1ba99efb7080d0818e018bf398aee742b63f6d778c`다.

- 0.9.8에서 CAN+Zipy 672·673번은 자동 보관 완료했다. PCAP은 각각 8,937·10,216패킷이며 CAN 정지 중 내부 전환도 성공했다.
- 674번의 CAN+Diag+Zipy도 모두 자동 보관 완료했다. Diag 정지는 808ms였고 trigger 정지·내부 파일 전환·BLF 완결·보관이 성공했다. Diag BLF는 455,380바이트·선언 객체 13,861개다. 현재 사용자가 이름을 바꾼 완료 파일에서도 CAN/CAN FD 프레임 13,844개·약 4.173초를 읽었다. 비-CAN 객체 header version 경고 두 건이 있어 모든 객체 해석이나 무손실을 보장하지 않는다. 복구가 필요한 미완료 파일이 아니다.
- 문제는 그 뒤 기존 Diag 출력 이름 복구다. cfg에 루트와 여러 `..`가 결합된 BLF 경로가 들어 있었고, CANoe에 복구를 요청해도 FullName이 내부 파일에 그대로 남았다. 세 번 복구 후 정지/보관은 성공 처리했지만 다음 prepare의 connect가 같은 복구를 필수로 다시 요구해 실패했다. 두 번째 실제 trigger 시작이나 번호 예약까지 도달하지 못했다.
- 라이선스·채널 오류가 아니다. 경로 유효성/권한 중 어느 이유로 CANoe가 그 이름을 거부했는지는 이 로그만으로 확정하지 않는다. cfg 원문에서도 해당 경로 형태를 확인했다. Windows 보안·폴더 권한은 바꾸지 않았다.

## 수정

1. 절대 기존 경로의 `..`를 정규화해 복구 요청한다. 원래 snapshot은 보존하고 cfg를 저장하지 않는다.
2. 여전히 거부되면 같은 cfg·선택 인덱스·블록 이름/전체 배치·다른 출력이 유지되고 AutoLog가 발행해 정지 확인한 출력/내부 파일이 정확히 맞는 경우에만 복구를 보류하고 다음 구간을 허용한다. 초기 경로 snapshot을 내부 이름으로 바꿔치기하지 않는다. 다음 configure는 새 작업 경로를 정확히 확인하고 기존 파일을 덮어쓰지 않는다.
3. 외부 출력/옵션·cfg·블록 변경이나 수동 trigger 활성 상태는 계속 차단한다. 측정을 다시 시작하거나 다른 CANoe/블록을 정지하지 않는다. 새 출력 적용이 실패해 이전의 확인된 idle 출력만 남은 경우에도 그 소유 근거를 유지한다.
4. 정상 종료에서도 해당 idle 상태라면 원래 경로 복구 실패만으로 COM 해제를 막지 않는다. 정지 미확인/외부 변경은 이 예외가 아니다. X 제한과 원본 보존 정책을 유지한다.
5. 사용자 활동에는 보관 오류와 구분되는 한·영·중 복구 보류 안내를 표시한다. 개발자로그에는 정규화 요청, 원래 snapshot, 현재 출력, 보류 원인과 다음 동작을 기록한다.

## 검증

기존 0.9.8 코드로 첫 BLF 완결 성공 뒤 두 번째 prepare가 `CANoe did not confirm restored output settings`로 실패하는 것을 대역에서 재현했다. 새 코드는 원래 이름의 raw/정규화 경로를 모두 거부하는 대역으로 CAN+Zipy·Diag+Zipy·CAN+Diag+Zipy 각각 연속 세 구간의 완료, 마지막 객체, 최종 파일, 번호, 원래 snapshot 보존, 측정 유지, 한 번만 cfg 열기와 내부 파일 정리를 검사한다. 정규화만으로 복구 가능한 경우, 외부 경로/활성 trigger/옵션/cfg/블록/선택 변경 거부와 종료 시 COM 해제도 검사한다.

실제 0.9.9 CANoe 반복 기록은 이 작업에서 수행하지 않았다. 같은 Diag cfg로 측정을 유지한 채 3회 이상 기록→정지→보관→다음 시작을 시험한다. 복구 보류 안내가 있더라도 매번 최종 BLF·프레임·번호를 확인하고, 외부 출력 변경이 없다면 다음 시작이 복구 오류로 막히지 않아야 한다. 고부하·장시간·차량 무손실 검증은 별도다.

전체 자동 검사 567개(57.33초), Ruff·의존성·diff와 문서 로컬 링크 280개를 통과했다. 마지막 내부 파일이 있는 경우와 Stop만으로 닫히는 경우 모두 새 출력 setter 실패 뒤 이전 idle 소유/원래 snapshot 유지와 다음 시작을 확인했다. 공식 가이드 2026-10-22.1을 PC/작은 폭 10개 뷰포트로 소프트웨어 렌더링하고 복구 보류·문제 해결·확인 범위의 내용과 배치를 확인했다.
