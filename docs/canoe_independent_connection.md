# cfg마다 CANoe 자동 독립 연결 — 0.8.4

사용자가 선택한 CAN/Diag cfg는 각각 독립 연결되어야 한다. 0.8.1~0.8.3은 필요한 연결 처리를 사용자 옵션으로 노출해 이 요구를 충족하지 못했다. 현재는 각 카드의 **연결 확인**만 사용한다.

## 연결 처리

- 첫 COM 생성 전에 등록된 CANoe 설치본의 `SingleCOMClient=1`을 필수로 준비한다. 기본값 0이고 CANoe 프로세스가 없다면 배타 파일 열기·원본 백업·한 바이트 변경·읽기 확인을 자동 수행한다. 준비할 수 없으면 공유 COM 생성으로 우회하지 않는다.
- 기본 모드 CANoe가 이미 실행 중이면 기존 작업을 저장하고 모두 닫은 뒤 재연결해야 한다. 이 경우 모드 선택을 묻지 않으며 다음 연결이 자동 준비한다. 기존 작업이나 창을 자동 종료하지 않는다.
- CAN/Diag worker의 설정 준비와 DispatchEx를 Windows 이름 있는 mutex로 직렬화한다. 각 활성화 전후의 프로세스 차이가 새 CANoe PID 하나인지 확인한다. 기존/불명확한 프로세스가 반환되면 cfg를 열어 덮어쓰지 않는다.
- 새 COM 객체가 미구성인지 확인한 뒤 선택한 정확한 cfg를 열고 경로를 다시 검사한다. 이후 해당 참조와 기록 블록을 대상별로 유지한다. 재연결은 이미 소유한 같은 창을 사용한다.
- 화면에서 모드 설정창과 켜기/복구 버튼을 제거했다. 각 카드에 연결된 cfg 파일명·전체 경로 툴팁·CANoe PID를 표시한다. 연결 실패·측정 정지·View Only는 구분한다.

이 설정은 CANoe 설치 전체에 유지된다. 설치 파일의 Vector 설명에는 다른 COM 도구·ActiveX/.NET 패널에서 추가 인스턴스가 생길 수 있다고 명시돼 있다. 일반 사용자 흐름에서 공유 연결로 전환하는 선택은 제공하지 않는다.

## 확인한 결과

- 전체 자동 검사 **379개**, Ruff를 통과했다. 자동 적용 후 COM 생성, 기존 프로세스 보존, 준비 불가 시 우회 차단, 새 PID 없음/여러 PID 거부, 양쪽 설정의 늦은 저장 응답, 정상 구간 제어와 파일 보존을 포함한다.
- 실제 CANoe 19.3.118에서 기존 프로세스가 없는 기본 모드 0부터 CAN/Diag worker에 동시에 연결을 보냈다. 최초 준비가 자동 적용되고 CAN PID **29164**, Diag PID **13932**가 생성됐다. 각 cfg 경로·BLF 기록 블록 1을 확인했다. 역순 재연결도 같은 두 PID와 구성을 유지했다.
- 별도 실행에서는 실제 Qt 설정의 CAN/Diag 연결 버튼을 연속 클릭해 UI→coordinator→worker 경로를 확인했다. CAN PID **26844**, Diag PID **36276**에 각각 연결됐고 각 카드·기억한 블록 선택도 일치했다.
- 두 실행 모두 원본 cfg의 전후 SHA256이 같았고 측정/Trigger Start·Stop을 호출하지 않았다. 이 PC의 View Only 상태에서는 실제 BLF 기록을 검증하지 않았다.
- 최초 계측 스크립트의 can.ini 전체 바이트 비교는 CANoe가 구성 열기 시 자체 갱신한 `LastCANoeConfigurations` 때문에 실패했다. 독립 모드 한 바이트 적용·읽기 확인과 최근 구성 이력의 CANoe 갱신을 구분한다. cfg 연결·두 PID·재연결·cfg 해시 검사는 통과했다.
- 근거: 로컬 `Downloads/AutoLog_Builds/hotfix-0.8.4-review/`의 `dual-result.json`, `ui-result.json`, `developer_logs/`와 화면 이미지. 원본 can.ini 백업은 같은 설치 설정 폴더에 남겨 두며 자동으로 기본값 0으로 복구하지 않았다.

현재 PC에는 필요한 독립 모드가 적용되어 있다. 현장 측정·BLF 완결과 라이선스·실제 장비 검증은 기존 계획에 따라 이어간다.
